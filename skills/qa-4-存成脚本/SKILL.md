# 第 4 步 · 把走通的存成脚本

AI 走一遍要花 token、结果每次可能不一样。走通一次之后，存成脚本：
**以后每次发版跑脚本，不再让 AI 走**。几十秒跑完，结果是确定的。

## 开始前

1. **先读项目根目录的 `项目适配.md`**。这个项目用什么工具、怎么登录、怎么等、能不能并行，以前踩过的坑都在里面。没有这个文件就按下面的默认做法来，做完把用到的做法写进去
2. 告诉用户**这一步要存哪几条**，从哪来的（`maps/` 里走过的页面，或 `reports/` 里判了「通过」的用例），等他点头

## 只存通过的

- 判了「通过」的 → 存
- 判了「失败」或「说不准」的 → **不存**。把 bug 当成预期写进脚本，脚本就会一直替 bug 作证

## 工具跟着项目走

- 项目里已经有测试工具 → 用它的
- 没有 → Web 默认 Playwright；App 用项目能跑的宿主侧脚本
- 定下来的写进 `项目适配.md`，下次不再问

## 写脚本的规矩

**定位**：只用用户看得见的东西——标题、按钮的名字、角色。不用 CSS class、不用 xpath。
按名字找元素**要精确匹配**：大多数工具默认是"包含"，「登录」会同时匹配到「游客登录」。

**等待**：不要写固定秒数。等一个"确实到了"的标志：
- 页面：等标题出现
- 数据：**等业务接口都返回**，不要等"网络完全安静"。有的前端框架（比如 Nuxt）页面出来后还会预加载别的页面的代码，等"安静"会白等，还会被拖到超时

**报错要说人话**：失败时要说清是哪一步、哪个接口、等了多久。
「有接口没返回」没用，「batch/page 等了 4835ms 没返回」才能查。

**每条测试独立**：每条从干净的状态开始，不依赖上一条的结果。这样一条挂了不连累下一条。

## 存完要跑，跑稳了才算存好

1. **先用一个浏览器跑**，全绿
2. **连跑 3 次全绿**，才算存好
3. 想并行再试并行。**时红时绿，先怀疑并发**：换回一个浏览器跑，如果稳了，就是被测系统扛不住并发。
   这时候**不要加自动重试来掩盖**，写进 `项目适配.md`，并且作为一条「说不准」报给用户——
   它可能是限流，也可能是真实的性能问题

**跑不稳的脚本不如没有。** 时红时绿几次，就没人再信它了。

## 告诉用户怎么看它跑

用户第一次跑，多半会问"为什么看不到浏览器在动"。提前说：

- 默认不开窗口，快、不打扰人
- 想看全程：用工具的界面模式（Playwright 是 `--ui`），一个窗口，能一步步回放
- 不要推荐"有头模式"看全程：每条测试一个新浏览器，会一直闪。有头模式只适合调单条

## 做完就停

告诉用户：存了哪几条、放在哪、连跑 3 次的结果、以后怎么跑（一条命令）。
然后**停下**，不要自己接着做下一步。

## ⚠️ 走不通必须上报，不准自己换路

存成脚本时发现原来走通的路现在走不通了：**停下来报告**，不要换一条路让脚本变绿。

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。
