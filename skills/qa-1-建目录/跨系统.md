# 跨系统 · 生成参考

只在第 6 问答了"多角色 / 上下游 / 两种都有"时读这个文件。

## 先分清两种，验的东西完全不一样

| | 多角色 | 上下游 |
| --- | --- | --- |
| 例子 | 买家下单 → 后台审核 → 买家看到状态 | 订单系统 → 库存系统 → 财务系统 |
| 验什么 | **流程通不通** | **数据有没有变形** |
| 入口 | 界面 | 经常不是界面（定时任务、导入、推送） |
| 典型 bug | 对方看不到、状态不同步 | 精度丢失、枚举映射错、时区差 8 小时、单位不一致、null 变 0、截断 |

**上下游最危险的地方：流程全绿，数据全错。** 金额差一分钱，三个月后对账才发现。
所以上下游用例必须做字段级对账，不能只看流程走没走完。

"两种都有"就两套都生成。

## 目录上的差别

```
seeds/.auth/
  c端-买家.json            ← 按「系统-角色」拆，一个角色一份登录态
  b端-审核.json

maps/
  c端/                     ← 按系统分目录
  b端/

prompts/02-no-touch.md     ← 按系统分段，每个系统一段
bindings/                  ← 上下游多两段：ID对照、数据位置（见下）
```

不新建目录。`bindings/` 原来是「业务语言 → 界面路径」，
上下游要的是「业务语言 → 数据在哪」——**本质是同一件事：把最易变的定位信息关在一层里**。
界面改了动前者，接口改了动后者，`cases/` 永远不动。

## bindings 模板（上下游）

```yaml
# 同一笔业务在各系统叫什么 —— 串链路的前提，先填这个
# 这张表不填，AI 根本串不起来
ID对照:
  订单系统: orderNo
  库存系统: bizNo       # = 订单系统.orderNo
  财务系统: outNo       # = 订单系统.orderNo

# 业务语言 → 数据在哪（接口改了只动这里）
数据位置:
  订单金额:
    订单系统: GET /api/order/{orderNo} → data.amount
    财务系统: GET /api/voucher?outNo={orderNo} → items[0].amount
  订单状态:
    订单系统: GET /api/order/{orderNo} → data.status
    财务系统: GET /api/voucher?outNo={orderNo} → items[0].bizState
    映射: { CANCELLED: 40, FINISHED: 30 }
```

## cases 模板

每类默认只生成 **1 条**样例。

### 多角色

```yaml
- id: X-01
  标题: 买家下单后，后台 30 秒内能审到
  规则: PRD 4.1
  步骤:
    - { 谁: C端买家,   做: 提交一笔 99 元订单 }
    - { 谁: B端审核员, 做: 在待审列表里找到该单 }
  预期:
    - 30 秒内出现在待审列表     # 同步时限本身就是一条规则，写进来
```

### 上下游对账

```yaml
- id: X-02
  标题: 订单金额和状态传到财务系统不变形
  入口: 调订单系统接口造一笔 99.99 元订单    # 上游入口不走界面
  时限: 60 秒
  对账:
    - { 字段: 订单金额, 要求: 完全相等，含小数位 }
    - { 字段: 订单状态, 要求: 按映射表转换后相等 }
```

### 逆向（最没人测、事故最贵的一类）

```yaml
- id: X-03
  标题: 财务入账失败时，订单不能显示已支付
  入口: 造一笔订单
  制造故障: 让财务系统入账接口返回 500
  预期:
    - 订单状态回退或标记异常，不是「已支付」
    - 库存没被扣，或者被补回来了
```

生成这条时要**如实告诉用户**：

> 浏览器发出的请求能直接拦截改成 500；
> 但**系统和系统之间的调用，测试工具拦不到**，
> 需要测试环境有故障开关或 mock 服务。
> 这是整套流程里**唯一大概率要找开发配合**的地方，
> 做不到就先把这条标成"待环境支持"，不要删。

同类还有：重复投递（同一条消息发两次，会不会扣两次库存）、超时重试、部分成功。
列给用户，让他挑，不要全生成。

## 生成时的三条硬规则

1. **跨系统用例提醒用户总数控制在 3~5 条主干**，只留钱路径。
   它的维护成本是单系统的 N 倍，任何一个系统改了都会挂；
   堆多了必然变成"天天红、没人看"，然后整套被废掉。
2. **同步等待一律轮询到条件成立，不准固定 sleep**，时限写进用例。
3. **后台的禁点清单默认比前台严。** 前台一个按钮影响一个账号，
   后台一个按钮可能影响全站：批量下架、清缓存、强制退款、改全局配置，默认全禁。
