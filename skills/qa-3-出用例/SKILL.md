# 第 3 步 · 补用例

## 开口第一行：报版本

开始做之前，**第一行单独写**：

```
QA 流水线 v1.7.0 · qa-3-出用例
```

就这一行，不加别的话，像软件标题栏那样。直接写出来，不用放进代码块。
版本号就是这个文件开头那行注释里的 `version`，**不要去磁盘上读文件来报** ——
你报的必须是你现在加载的这一份。学员出问题时，作者靠这一行知道他跑的是哪一版。

接着顺手比一下（找得到就比，找不到就跳过，不要卡住）：

- skill 目录里 `qa-更新/版本.json` 的版本比你报的新 → 这个对话加载的是旧版。
  告诉用户「skill 已经更新了，但这个对话还在用旧版，请重启 AI 工具或者开一个新对话，再打这个命令」。
  他说「继续」，就照你现在这一版接着做，不要拦着
- 项目里 `.qa-ai.json` 的版本比你报的新 → 这个项目是更新的版本建的，提醒他先打 `/qa-更新`

这一步新写或改过的文档（用例清单、覆盖表、审核表、问题单），标题下面写一行
`生成：QA 流水线 v1.7.0 · qa-3-出用例 · <日期>`。改已有的文档，把这一行改成这一次的。

**扫页面时的用例不归这一步。** `/qa-2-扫一遍出脚本` 扫到哪，用例和脚本就当场写到哪。
这一步只管三种情况：

| 情况 | 做什么 |
| --- | --- |
| **有 PRD / 需求，功能还没做出来**（开发阶段） | 照 PRD 写用例，`状态: 待实现`，先不写脚本。提测了改成 `已提测`，当场写脚本跑 |
| **有 PRD / 规则文档了，功能已经在跑** | 照文档补用例；**已有的基线用例对得上文档的，升级成有依据的**（见下） |
| **要给别人看** | 导出，见「要给别人看」 |

用户不想手写用例。**你写，有要他定的才进审核表。**

## 开始前

1. 读项目根目录的 `项目适配.md`。
   **没有就当场建一个**：按 `qa-1-建目录` 那个 skill 目录里的 `项目适配模板.md`，
   只建这一个文件，别的不动，建完告诉用户。
2. 读同目录的 `写用例.md`，用例怎么写全照它；写脚本照 `qa-4-跑测试/写脚本.md`；判挂了的照 `qa-4-跑测试/缺陷门槛.md`。
3. 要 PRD、需求文档：他提到了就要过来。规则文档在哪，记进 `项目适配.md`，以后每一步都先读它。
4. 读 `地图/覆盖表.md` 和 `用例/用例清单.md`，知道已经有哪些。**已提测的功能还没扫过的**，先让他跑 `/qa-2-扫一遍出脚本`，
   这一步不凭菜单名猜着写。

## PRD 跟成品对不上

**照 PRD 写用例，标 `冲突待裁决`。**
不准自己选一边，尤其不准默认"以成品为准"——那等于永远不报 bug。
脚本照 PRD 写断言，挂了判「说不准」，在审核表「变了，变得对不对」那一段列出两边差异，他来裁决。

## 有了规则文档：把基线升级成真规则

扫的时候没有原文、按现状存成 `基线` 的用例，**有了文档就能升级**：

1. 逐条对：这条基线的行为，文档里有没有写
2. 写了、而且跟基线一样：`预期来源` 改成 `PRD · 第几条`，最近判定由 `没变` 改成 `通过`。脚本不用动
3. 写了、但跟基线**不一样**：断言改成文档写的样子，跑一次。挂了就是违反了原文，照 `缺陷门槛.md` 判，过了门槛的写问题单、进审核表
4. 没写：保持基线

收尾时报：升级了几条、几条跟文档对不上（写了几张问题单）、几条文档里没提。
**这是把"只防变化"变成"验过对错"的唯一途径**，基线多的项目，有文档就值得做一遍。

## 写完就写脚本、就跑

已提测的用例，写完当场照 `写脚本.md` 写成脚本，跑一次、再连跑两次，跟扫页面时一样。
挂了的：脚本没写对就改脚本；过了缺陷门槛的写问题单、标 `问题-xx 待确认`、进审核表；说不出原文的判「说不准」，不写问题单。

`待实现` 的不写脚本，「脚本」列写 `未存：待实现`。

## 要他定的：只进审核表

**不再把新用例一条条交给他审。** 有原文、通用规律的直接能判，基线不用审。
只有这几种进 `用例/审核表.md`，格式和他说「审完了」之后怎么改，照 `qa-5-提bug/审核表.md`：

- 过了缺陷门槛的问题（「是不是 bug」）
- `冲突待裁决` 的（「变了，变得对不对」，写清 PRD 怎么说、系统怎么做）

流程简称起得他看不懂的，他在用例清单里直接改就行，不用专门审。

## 要给别人看：导出用例

用户要把用例发给同事、拿去评审、导进用例平台的，**读同目录的 `导出用例.md`，照着做**。
每个团队的格式都不一样，第一次先问清楚、记进 `项目适配.md`，下次直接出。

只是导出、不写新用例的，开口照样报版本，做完照收尾格式报，下一步说「等评审意见回来再打 `/qa-3-出用例`」。

## 不要做的事

- **不要把没依据的现状说成规则**。没原文的写 `基线`，不要写成产品说明
- **不要写「点击第 3 个按钮」这种步骤**。用业务语言写，让不懂技术的人也能看懂

## 收尾前：检查要不要写进 `项目适配.md`

逐条过一遍。**有任何一条，就必须写进「踩过的坑」**（做法 / 为什么 / 日期）：

- 这个项目的规则写在哪（PRD 在哪、产品说明在哪）
- 有些流程只能在某个账号或某个环境下测
- 某个流程有不可逆的步骤，测完要手工清理

收尾汇报里**必须有一行**：`项目适配.md：补了 N 条（逐条列出）` 或 `项目适配.md：这次没补`。

## 提到的文件和编号，都写成能点开的链接

- **对话里**：提到文件就写成 `[问题-07](报告/2026-10-10/疑似问题/问题-07.md)`，路径从项目根目录算
- **写进文档里的**：每个编号、每个证据文件都写成链接，路径从**这份文档所在的目录**算
- 编号链到它的出处：用例 → 那条用例所在的 yaml；问题 → 它的问题单；已知 → `校准/已知bug.md`
- **写完把每个链接对一遍文件在不在**。断掉的链接比没有链接更误导人

## 对话长了、被压缩了怎么办

**进度随时落到文件里**：写一批就写进 `用例/` 的 yaml、`脚本/`、`用例清单.md`。

**发现对话被压缩过**（对话开头变成了一段摘要）：**先重读再继续** —— 这个 skill 的说明、
`项目适配.md`、`提示词/02-禁点清单.md`，还有记进度的那个文件。不要凭摘要里的印象往下走。

**这一轮对话已经很长**：收尾时提醒一句「下一个命令可以在新对话里打，进度都在文件里」。对话不长就不用提。

## 收尾：照这个格式报，一条都不能少

1. **这一步动了哪些文件**：按目录分组，新增还是修改，每个一句话
2. **没动哪些**：列出来
3. **现在去看哪个文件**：有要他定的是 `用例/审核表.md`，没有就是 `用例/用例清单.md`
4. **这轮读了几屏、脚本跑了几次、大约多少 token**（说清这不是总数，以 AI 工具自己显示的用量为准）
5. `项目适配.md`：补了 N 条（逐条列出）或 这次没补
6. **下一步打哪个命令**

这一步额外要说：写了几条、几条存成了脚本、几条待实现；升级了几条基线；要他定的几条。

**收尾前你自己先把下面这几条查一遍**，在收尾里报结果：每条一句「过了」或「没过：原因」，带上能点开的文件链接：

- 每条的预期来源能不能追到原文、规律或日期；没依据的老实写了 `基线`，没有冒充产品说明
- 已提测的每条，「脚本」列有值，「最近判定」有值
- 写成问题单的每一条都能指出违反了哪条原文
- `地图/覆盖表.md` 的「用例」列跟着填了

有要他定的，**一句话指向审核表**，不在对话里列。说完**停下**。
他说「审完了」，在这个对话里就照 `qa-5-提bug/审核表.md` 改；新对话打 `/qa-5-提bug`。没有要定的，下次提测打 `/qa-4-跑测试`。

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。

**老的审核表里还有「待审」的批次**（1.7.0 以前那种逐条审用例的）：照旧处理——他说「审完了」，空着的算对，
`预期来源` 改 `用户确认 · 日期`；然后脚本断言跟着改，按编号跑一次。没说就不动，那几条照旧最多判「说不准」。

目录还是英文名的（`cases/`、`maps/` 这些）：按 `qa-1-建目录` 那个 skill 目录里的 `目录对照.md`
找对应的英文目录，照常做，**不要新建中文目录**。做完提一句：「跑一次 `/qa-1-建目录` 可以改成中文目录」。
