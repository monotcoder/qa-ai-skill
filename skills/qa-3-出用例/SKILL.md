# 第 3 步 · 起草用例，交给人审

## 开口第一行：报版本

开始做之前，**第一行单独写**：

```
QA 流水线 v1.4.0 · qa-3-出用例
```

就这一行，不加别的话，像软件标题栏那样。直接写出来，不用放进代码块。
版本号就是这个文件开头那行注释里的 `version`，**不要去磁盘上读文件来报** ——
你报的必须是你现在加载的这一份。学员出问题时，作者靠这一行知道他跑的是哪一版。

接着顺手比一下（找得到就比，找不到就跳过，不要卡住）：

- skill 目录里 `qa-更新/版本.json` 的版本比你报的新 → 这个对话加载的是旧版。
  告诉用户「skill 已经更新了，但这个对话还在用旧版，请重启 AI 工具或者开一个新对话，再打这个命令」。
  他说「继续」，就照你现在这一版接着做，不要拦着
- 项目里 `.qa-ai.json` 的版本比你报的新 → 这个项目是更新的版本建的，提醒他先打 `/qa-更新`

这一步新写或改过的文档（地图、覆盖表、用例清单、报告、问题单、变更单），标题下面写一行
`生成：QA 流水线 v1.4.0 · qa-3-出用例 · <日期>`。改已有的文档，把这一行改成这一次的。

用户不想手写用例。**你起草，他审。** 读一条业务语言的用例十几秒，写一条要十分钟。

## 两种入口，都要支持

| 什么时候用 | 有没有 PRD | 怎么起草 | 用例的 `状态` |
| --- | --- | --- | --- |
| **开发阶段**：功能还没做出来 | 有 | 照 PRD 写，先写后做 | `待实现`，做完提测了改成 `已提测` |
| **测试阶段**：功能已经在跑了 | 没有 / PRD 跟页面对不上了 | 走一遍页面 + 下面四类来源 | `已提测` |

**PRD 跟成品对不上时，照 PRD 写用例，标 `冲突待裁决`。**
不准自己选一边，尤其不准默认"以成品为准"——那等于永远不报 bug。
跑出来判「说不准」，把两边的差异列给用户，他来裁决。

## 没有 PRD 时，预期从哪来

**不能拿"系统现在就是这样"当预期。** 那是拿系统证明系统，bug 会被原样抄成预期。
可以用的有四类，没有一类是"代码现在怎么跑的"：

| 来源 | 例子 | 为什么可信 |
| --- | --- | --- |
| **产品自己的说法** | 首页文案、界面提示、按钮名、帮助文档、错误提示 | 文案是人写的，逻辑是代码写的，两套东西能互证 |
| **不依赖需求的规律** | 不崩、数字自洽、写进去能读回来、状态不倒退、看不到别人的数据、重复提交不产生两条 | 任何系统都该成立 |
| **两个端互相验证** | PC 发布的批次，小程序和消费者页看到的必须一致 | 两个实现，对不上就一定有一个错 |
| **上一版的行为（基线）** | 跟上一版比，哪里变了 | **只能证明"变了"，不能证明"对"**。报告里必须写明这一点 |

都没有，才标 `AI推测`，等用户确认。

## 用户确认过的猜测，就是需求

用户点头之后：

```yaml
预期来源: 用户确认
确认于: 2026-09-23
原本是: AI推测 · 统计报表里有「草稿批次」这一项
```

**记上日期，别丢掉"原本是猜的"这句。** 攒下来，这份用例库就是这个项目
事后补出来的需求文档——很多项目本来就没有那一份。

## 开始前

1. 读项目根目录的 `项目适配.md`。
   **没有就当场建一个**：按 `qa-1-建目录` 那个 skill 目录里的 `项目适配模板.md`，
   只建这一个文件，别的不动，建完告诉用户。
2. 问用户：**有没有 PRD、需求文档、产品说明？** 有就要过来，这是最好的预期来源。
3. 读 `地图/覆盖表.md` 和 `地图/` 里走过的页面。没有就先让他跑 `/qa-2-走一遍页面`。
   **只给走过的部分出用例**，没走的不要凭菜单名猜着写

## 每条用例的预期，必须标明从哪来

**这是这一步最要紧的一条规矩。**

| 预期来源 | 怎么用 |
| --- | --- |
| `PRD` | 直接用，写清楚是哪一条 |
| `产品说明` | 直接用，**把原文抄进来**（首页文案、帮助文档、界面上的提示都算） |
| `通用规律` | 不依赖需求、任何系统都该成立的（必填不填不能保存、翻页不丢数据、看不到别人的数据）。直接用，写清是哪一条规律 |
| `用户确认` | 原本是 AI 猜的，用户点头了。记上日期 |
| `基线` | 照上一版行为存的。通过只代表**没变**，不代表对 |
| `冲突待裁决` | PRD 跟成品对不上，人还没裁决。**只能判「说不准」** |
| `AI推测` | **用户点头之前，跑出来最多只能判「说不准」，不准判「通过」** |

最后一条不能松。AI 看着页面猜预期，等于**拿系统现在的样子证明系统是对的**——
系统本来就错了的地方，会被原样抄成"预期"，然后永远绿着。

用户审过的，把 `预期来源` 改成 `用户确认`，那条才能判「通过」。

**只用上面这 7 个，不要自己起新名字**（比如「两端互证」「常识」）。后面几步按这 7 个名字决定能判到哪一档，
认不出的名字就没法判。两处显示同一份数据该一致、无障碍这类，都算 `通用规律`，后面写清是哪条规律。

## 按覆盖表逐个功能点出

**用例不是从"想到什么写什么"来的，是从覆盖表一格一格过出来的。**
覆盖表里每个「走过」的功能点，按它的类型对照这张清单，该有的都要有：

| 类型 | 至少要有 |
| --- | --- |
| 列表 | 能打开、条数和别处一致、搜索、筛选、翻页、空状态、导出（有导出的话） |
| 表单 | 必填不填不能保存、格式不对有提示、边界值（最长、最小、0、负数）、重复点提交只生成一条、取消后不保存 |
| 详情 | 字段和列表里显示的一致 |
| 删除 / 作废 | 有二次确认；有关联数据时怎么处理（能不能删、删了关联的怎么显示） |
| 状态流转 | 每个状态能到哪些状态、不能倒退 |
| 跨端 | 一端改了，另一端看到的一致 |

**清单里大多数是 `通用规律`**，不用等用户逐条点头就能判通过；
**产品规则才需要他确认**（免费额度是几条、过期批次要不要标红）。这样用例多了，他要审的不会跟着翻倍。

出完把覆盖表的「用例」那一列填上：

| 情况 | 「用例」列写什么 |
| --- | --- |
| 出了 | 编号，写成链接：`[商品-01](../用例/商品库.yaml)` |
| 清单里这一项不适用 | `不适用：没有导出按钮` |
| 该有但出不了 | `没出：<原因>`，比如「读了字段没提交，不知道保存后会怎样」 |
| 这个功能点还没走 | 留空，等 `/qa-2-走一遍页面` 走过了再出 |

**一次出不完就分几次。** 用例清单的「审了没」和覆盖表的「用例」列就是进度，新对话接着出。

## 走页面时记的那些怀疑，一条都不要浪费

`地图/` 的 `notes` 里有一堆怀疑，按这张表分流：

| 情况 | 怎么办 |
| --- | --- |
| 用户确认是 bug | 进 `校准/已知bug.md`，编号 `已知-xx`、写明从哪个 `问题-xx` 来，**同时写一条用例**。这条跑出来就该是红的，修好了自己变绿 |
| 能说清"正确应该是什么样" | 写成用例，标好预期来源 |
| 说不清正确是什么样 | **列给用户，问他预期应该是什么**，别自己编一个 |
| 核实不了、坐不实 | 丢掉，不要凑数 |

第一行最要紧：**已知 bug 必须有对应的用例**。校准集的意义就是
"已知的 bug 必须被抓到" —— 抓不到，说明这套东西在装瞎。

## 按流程分组，每条给编号

用户回归时是按**流程**说话的：「跑一下批次发布」。所以用例要按流程分组：

```yaml
流程: 批次发布
说明: 从新建批次到消费者扫码能看到
用例:
  - id: 批次-01
    标题: 新建批次后是草稿状态
    前置: 用固定数据里的测试账号登录
    步骤:
      - 进入生产批次
      - 新建一个批次，名字用 QA-AI- 开头
      - 保存
    状态: 已提测          # 待实现 / 已提测 / 待数据（缺前置数据，有了再跑）
    范围: 冒烟            # 冒烟 / 全量 / 要用户准备
    前置数据: 无          # 要什么数据、谁准备、怎么准备
    预期: 列表里出现这个批次，状态是「草稿」
    预期来源: AI推测 · 统计报表里有「草稿批次」这一项
  - id: 批次-02
    标题: 草稿提交后进审批中心
    步骤: [...]
    预期: 审批中心的「批次」数量 +1
    预期来源: 产品说明 · 首页原文「两步审批工作流（审批→发布）」
```

### 编号怎么起

**编号要让人一眼看懂，不用字母缩写。** `X-01`、`R-02` 这种，除了起名的人谁也不知道是什么。
测试文档的标准只要求编号唯一，格式没规定，所以按看得懂来定：

| 什么 | 格式 | 例子 | 怎么排号 |
| --- | --- | --- | --- |
| 用例 | 流程简称-两位序号 | `批次-01`、`隔离-02`、`证书-01` | 每个流程各自从 01 排 |
| 疑似问题 | `问题-` 两位序号 | `问题-07` | **整个项目连续排**，换一天不从 01 重来 |
| 已知 bug | `已知-` 两位序号 | `已知-05` | 整个项目连续排，写明是从哪个问题来的 |
| 提到 bug 平台之后 | 用平台给的号 | `TJT-123` | 写回那个疑似问题里，不另起编号 |

流程简称：

- **两到四个字**，取流程名里最有辨识度的那几个字：「批次发布」→ `批次`，「多租户隔离」→ `隔离`
- **一个流程一个简称，两个流程不准共用**。起名时先看一眼 `用例清单.md` 里已有的
- 简称是你起的，**交给用户审用例时一起审**。他觉得不好懂就换

老项目 `.qa-ai.json` 里写着 `"编号": "字母"` 的，用户选了不改：新用例**接着用这个项目原来的格式**，一个项目里不混两套。

编号一旦给出去就**不改、不复用**：删掉的用例，它的号空着，不给新用例。
报告、问题单、脚本里都引用过这个号，改了或复用了，历史记录就对不上了。

**`用例/` 里不准出现任何选择器**（CSS、xpath、testid 一个都不行），
只写业务语言。怎么点是 `绑定/` 的事，界面改了只动那一层。

### 范围怎么分

| 范围 | 什么样的用例 |
| --- | --- |
| `冒烟` | 高频跑的就这一批。**副作用按下面那张表判，不是一刀切** |
| `全量` | 会留下痕迹（新建数据、让计数 +1、发通知），完整回归时才跑 |
| `要用户准备` | 要先腾额度、造特殊数据。**跑之前必须用户明说可以跑** |

判断标准不是"有没有副作用"，而是**跑一百遍之后，这个系统会不会变得不像样**：

| 副作用 | 能进冒烟吗 |
| --- | --- |
| 每轮固定一次、可计量、可记录（扫码量 +1、阅读量 +1） | 可以，记进副作用表 |
| 累积性的（每跑一次多一条数据） | 不行 |
| 不可逆的（删除、作废、扣费） | 不行 |
| 对外可见的（发短信、发邮件、推送给真人） | 绝对不行 |

扫码量多一百次没事，多一百条垃圾数据就有事了。

同一轮里要多条用例都打开同一个会计数的页面，**合并成一次打开，一次把几条都验完**。

### 前置数据：谁准备，写清楚

要新建数据、要腾免费额度、要造过期数据的，在用例里写明白：
要什么、谁准备、怎么准备。**不要自己删用户的数据去腾位置** ——
删是不可逆的，哪怕用户之前说过"随便改"，删之前也要单独问一次。

**预期别靠"线上现在有几条"**。线上数据会变，自己以后造的数据也会算进去：

- 搜空状态：搜一个**一定不会有**的词，比如 `不存在-20261015-xq7`。不要用测试数据的命名前缀（`QA测试`），
  哪天造了数据，这条就假失败
- 搜得到：断言"结果里有这一条"，不要断言"共 1 条"
- 数量变化：断言"比操作前多 1"，不要断言"等于 2"

## 还要出一份 `用例/用例清单.md`

一页纸，让用户不用翻文件就知道有什么、怎么点名。
**用文字写"已确认/未审"，不要用勾选框这类符号字符**：

```markdown
| 流程 | 编号 | 一句话 | 预期来源 | 范围 | 状态 | 审了没 | 最近判定 | 脚本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 批次发布 | [批次-01](批次发布.yaml) | 新建后是草稿 | AI推测 | 全量 | 已提测 | 未审 | 还没跑 | 未存 |
| 批次发布 | [批次-02](批次发布.yaml) | 提交后进审批中心 | 产品说明 | 冒烟 | 已提测 | 已确认 | 失败 · [已知-03](../校准/已知bug.md) | 已存 · 等修 已知-03 |

回归时怎么说：「跑冒烟」／「跑全量」／「跑批次发布」／「跑批次-02 到批次-04」
```

新起草的用例，「最近判定」写 `还没跑`，「脚本」写 `未存`。
这两列之后由 `/qa-4-跑测试`、`/qa-5-提bug`、`/qa-6-存成脚本` 回写，**是下一个对话的记忆**：
新开的对话只读这张表，就知道每条走到哪了。

## 交给用户审

**不在对话里一条条问，也不让他一条条标。** 大部分用例是没问题的，逐条问、逐条标都是浪费：
用户烦，每来回一轮还要把前面的对话重读一遍，费 token。

改成：**你写一张审核表，他只在不对的那几行写意见，其余空着；他说「审完了」，空着的就算「对」。**

### 写 `用例/审核表.md`

每起草一批，在文件**最上面**加一节（旧的批次往下排，留着当记录）。
**AI 猜的放最前面**，那是他真正要花心思看的；有原文依据的放后面，扫一眼就行：

```markdown
# 用例审核表

## 第 2 批 · 2026-10-15 · 待审

生成：QA 流水线 v<版本号> · qa-3-出用例 · <日期>

**怎么审：只在不对的那一行写意见，没问题的空着。** 看完了回到对话里说「审完了」，空着的都算「对」。
意见可以写：`不对：应该是……` ／ `删` ／ `不知道`。想看完整步骤，点编号。

### 先看这几条：预期是 AI 猜的（3 条）

| 编号 | 一句话 | 预期 | AI 凭什么这么猜 | 你的意见 |
| --- | --- | --- | --- | --- |
| [批次-01](批次发布.yaml) | 新建后是草稿 | 列表里出现这个批次，状态「草稿」 | 统计报表里有「草稿批次」这一项 | |

### 有依据的，扫一眼（7 条）

| 编号 | 一句话 | 预期 | 依据 | 你的意见 |
| --- | --- | --- | --- | --- |
| [批次-02](批次发布.yaml) | 提交后进审批中心 | 审批中心的「批次」数 +1 | 产品说明：首页「两步审批工作流」 | |
```

- 「预期」写**一句话能看懂的**，长的放 yaml 里，点编号能看
- 「依据」照抄 yaml 里的 `预期来源`
- 他想在 Excel 里审的：按 `导出用例.md` 导一份带「你的意见」列的，规矩一样，空着算对，审完放回项目里，照那份文件第 7 步读回来

写完在对话里**只说一句**：「这批 N 条，其中 M 条是 AI 猜的，放在最前面。打开 [用例/审核表.md](用例/审核表.md)，
只在不对的那行写意见，看完说『审完了』」。**不要把用例再抄一遍到对话里。**

### 他说「审完了」：读这一批，改用例

| 你的意见那一格 | 你做什么 |
| --- | --- |
| 空着 | 算「对」：`预期来源` 改成 `用户确认 · <日期>`（原来是产品说明、PRD 的，保留原来源，后面加 `· 用户确认 <日期>`），「审了没」改「已确认」 |
| `不对：应该是……` | 按他写的改 yaml 的 `预期`，`预期来源` 写 `用户确认 · <日期>`，「审了没」改「已确认」 |
| `删` | 从 yaml 和 `用例清单.md` 里删掉 |
| `不知道` | 不动，保持 `AI推测`，「审了没」写「用户也不确定」，收尾时列出来 |
| 看不懂他写的 | 只把这几条拿到对话里问，别的照上面处理 |

处理完，把这一节的标题改成 `已处理 · <日期>`，空着的格子填上 `对（默认）`，**让他以后翻得到当时是按什么处理的**。
在对话里报一句：按「对」处理几条（其中 AI 猜的几条）、改了几条、删了几条、不确定几条。
他事后发现哪条不对，直接在那一格改，说「审核表改了」，你再读一遍那一节。

**「空着算对」只在他说了「审完了」之后才成立。** 他没说、或者说的是「先这样」「回头再看」，
这一批就还是待审，`预期来源` 保持原样，AI 猜的照旧最多判到「说不准」。

## 要给别人看：导出用例

用户要把用例发给同事、拿去评审、导进用例平台的，**读同目录的 `导出用例.md`，照着做**。
每个团队的格式都不一样，第一次先问清楚、记进 `项目适配.md`，下次直接出。

只是导出、不起草新用例的，开口照样报版本，做完照收尾格式报，下一步说「等评审意见回来再打 `/qa-3-出用例`」。

## 不要做的事

- **不要把当前系统的行为直接抄成预期**。你看到状态显示「草稿」，那是现状，不是规则。
  没有依据就老实标 `AI推测`
- **不要在这一步跑用例**。这一步只写，跑是 `/qa-4-跑测试` 的事
- **不要写「点击第 3 个按钮」这种步骤**。用业务语言写，让不懂技术的人也能看懂

## 收尾前：检查要不要写进 `项目适配.md`

逐条过一遍。**有任何一条，就必须写进「踩过的坑」**（做法 / 为什么 / 日期）：

- 这个项目的规则写在哪（PRD 在哪、产品说明在哪）
- 有些流程只能在某个账号或某个环境下测
- 某个流程有不可逆的步骤，测完要手工清理

收尾汇报里**必须有一行**：`项目适配.md：补了 N 条（逐条列出）` 或 `项目适配.md：这次没补`。

## 提到的文件和编号，都写成能点开的链接

谁也记不住 `问题-07`、`已知-05` 底下是什么内容。所以：

- **对话里**：提到文件就写成 `[问题-07](报告/2026-10-10/疑似问题/问题-07.md)`，路径从项目根目录算
- **写进文档里的**（报告、变更单、用例清单、已知 bug、问题单）：每个编号、每个证据文件都写成链接，
  路径从**这份文档所在的目录**算（变更单在 `报告/2026-10-12/` 下，链 10-10 的问题单就写 `../2026-10-10/疑似问题/问题-07.md`）
- 编号链到它的出处：用例 → 那条用例所在的 yaml；问题 → 它的问题单；已知 → `校准/已知bug.md`
- **写完把每个链接对一遍文件在不在**。断掉的链接比没有链接更误导人
- 回放这种点开要下载的，链接旁边照样写上打开它的命令

## 对话长了、被压缩了怎么办

**进度随时落到文件里**：起草一批就写进 `用例/` 的 yaml、`用例清单.md`（「审了没」写未审）和 `审核表.md`。审核意见本来就在 `审核表.md` 里，对话断了也不丢。
这样不管是工具自动压缩对话、断网，还是用户中途关掉，都不会白做。

**发现对话被压缩过**（对话开头变成了一段摘要）：**先重读再继续** —— 这个 skill 的说明、
`项目适配.md`、`提示词/02-禁点清单.md`，还有记进度的那个文件。不要凭摘要里的印象往下走，
摘要里不一定还留着禁点清单的每一条。

**这一轮对话已经很长**（走完了一个模块、跑了十几条用例、来回几十轮）：收尾时提醒一句
「下一个命令可以在新对话里打，进度都在文件里」。开新对话比压缩好：压缩留下什么你控制不了，
新对话从文件里读，什么都不会丢。对话不长就不用提。

## 收尾：照这个格式报，一条都不能少

1. **这一步动了哪些文件**：按目录分组，新增还是修改，每个一句话
2. **没动哪些**：列出来
3. **现在去看哪个文件**：一般是 `用例/用例清单.md`
4. **这轮读了几屏、用的哪种读法、大约多少 token**
   token 只能估读页面那一部分，**报的时候说清这不是总数**：每多一轮对话，前面的内容都要重读一遍，
   整个对话的消耗通常是读页面的几十倍，以 AI 工具自己显示的用量为准
5. `项目适配.md`：补了 N 条（逐条列出）或 这次没补
6. **下一步打哪个命令**

这一步额外要说：**覆盖到哪了**（覆盖表里几个模块有用例、几个还没走、几个走了但没出）、
没覆盖的以后怎么补（「打 `/qa-2-走一遍页面` 说继续走没走的，走完再打 `/qa-3-出用例`」）；
起草了几条、分了几个流程、几条是 `AI推测` 等他确认、
几条缺前置数据跑不了、哪些怀疑因为依据不够没写成用例。

**收尾前你自己先把下面这几条查一遍**，在收尾里报结果：每条一句「过了」或「没过：原因」，带上能点开的文件链接，他想抽查点开就能看。**你能查的事不要甩给用户去查**。没过的，能改就先改好再收尾：

- 打开 `地图/覆盖表.md`：走过的功能点，「用例」那一列是不是都填了，没出的有没有原因
- 打开 `用例/用例清单.md`：每条的预期来源能不能追到原文或日期
- AI 猜的有没有老实标 `AI推测`，还是全写成了产品说明
- 范围和前置数据写了没有，不然跑起来才发现要腾额度

**只有他能定的，就是审核表**：让他去 `用例/审核表.md` 看，不要再另外列一堆让他检查的事。

**最后让他去 `用例/审核表.md` 看，只在不对的行写意见**，不要把用例抄进对话。
说完**停下**，等他说「审完了」。审完才能 `/qa-4-跑测试`；没审的照样能跑，但最多判到「说不准」。

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。

目录还是英文名的（`cases/`、`maps/` 这些）：按 `qa-1-建目录` 那个 skill 目录里的 `目录对照.md`
找对应的英文目录，照常做，**不要新建中文目录**。做完提一句：「跑一次 `/qa-1-建目录` 可以改成中文目录」。
