# 扫页面：扫一遍，当场存成脚本

`/qa-测` 定了这次要扫页面时读这份。平台文件、`项目适配.md`、禁点清单，`SKILL.md` 第 2 节已经读过了。

## 这件事做什么

**页面只读一遍。** 读到一个功能，当场写成用例、写成脚本、跑一次，跑完就是回归。
不再"先走一遍记怀疑 → 再出用例等审 → 再跑 → 再存脚本"，那样同一个页面要读三遍、用户要确认三次。

用户只在最后看一张审核表，里面只有**只有他能定的**那几行。常常一行都没有。

**报问题很克制**：只报过了 `缺陷门槛.md` 的。没有原文依据的行为，
按系统现在的样子写成 `基线`，**不报、不问**，以后变了才提一句。

全程零点击 —— 用户不碰鼠标。

## 开始前

1. 读这三份规矩，扫的活全照它们做：
   - `写用例.md`：用例怎么写、预期从哪来、按功能点类型该有哪些
   - `写脚本.md`：脚本怎么写、怎么标记、怎么算跑稳
   - `缺陷门槛.md`：什么才报
2. **看一眼项目里有没有现成的规则**：PRD、需求文档、帮助文档，项目里或 `项目适配.md` 里提过的。有就读，作为预期的原文。
   **没有就直接开始，不要停下来问一串问题**：没有原文的就写基线，规则是在后面审核表一来一回里慢慢补起来的。
3. 确认登录态还有效，怎么确认按平台文件。
   **三个端都一样：一个环境同时只能登一个账号。** Web 要换账号就换一个互相隔离的浏览器环境；
   安卓和小程序只能退出重登，或者换一台设备 / 换一个微信号，不要在同一个里反复切。
4. **确认写脚本的工具能用**：按平台文件「存成脚本用什么」那一节。缺什么一次列给用户，他点头才装。
   没法自动化的（没源码的小程序、还没有平台文件的端）：照样扫、照样写用例，「脚本」列写 `不适合存：没法自动化`
5. **看 `地图/覆盖表.md`**。有 → 这是接着扫，看用户这次要扫哪块（见「接着扫」）；没有 → 第一次，从「先读骨架」开始
6. **告诉用户能不能看、怎么看**。他看得见你在操作吗（Web 是浏览器窗口，安卓是设备或模拟器屏幕，
   小程序是开发者工具）？看不见就直说，并告诉他怎么打开。

## 先读骨架（几分钟）

不管后面怎么扫，**第一次都先把整个站的骨架读出来**：

- 每个菜单入口点进去，**只读这一页的一级标题和主要按钮**，不往深处走
- 用户菜单、顶栏里的入口也算
- 写进 `地图/覆盖表.md`：每个模块一行，有哪些页面、看得到哪些表单和弹层的入口

骨架读完，你就知道这个站有多大，才能跟用户说清楚几种扫法各要多久。

## 让用户选扫法

把骨架报给他（几个模块、几个页面、几个表单），然后**让他选，说清利弊**：

| 扫法 | 扫什么 | 好处 | 代价 |
| --- | --- | --- | --- |
| **先扫核心流程**（第一次推荐） | 一条从头到尾的主干业务，比如「建商品 → 建批次 → 发标签 → 消费者扫码看到」 | 半小时左右就有一套能反复跑的脚本，**马上看到这套东西有没有用** | 只覆盖这一条线 |
| **全部扫完** | 覆盖表里每个模块、每个页面的功能点 | 一次把全项目变成回归脚本 | 按骨架估时间告诉他（见下），token 也多几倍 |
| **指定模块** | 他点名的那几个 | 只测这次改了的地方 | 别的不知道 |

**估时间**：按骨架的大小报一个大概的数，比如「13 个模块、10 个表单，全扫完大约 1 到 3 小时」，
并说明这是粗估。扫过一次的项目，按上次每个模块花的时间估，更准。

**核心流程是哪条，你提一个，他定。** 从首页的产品介绍、菜单的顺序里找：
这个产品存在的理由是什么，从开始到最终用户看到结果要经过哪几步。

**他选了先扫核心流程，收尾时必须说清楚两件事**：
- **这次只扫了哪条线**，覆盖表里还有几个模块没扫
- **以后怎么接着扫**：打 `/qa-测`，说「继续扫没扫的」「扫商品库」或者「全部扫完」

## 一个模块怎么扫

**一个模块一批，不要一页一聊。**

1. **读**：把这个模块的页面按下面「每个页面扫到什么程度」读完，写进 `地图/` 和 `绑定/`
2. **写用例**：按 `写用例.md` 的「按覆盖表逐个功能点写」，每个功能点该有的都写上。
   每条的预期都标来源：有原文的照原文；任何系统都该成立的是 `通用规律`；**都没有的写 `基线`，照你现在看到的样子写**
3. **写脚本**：照 `写脚本.md`，一条用例一个测试，这个模块一个文件
4. **跑**：先跑一次。挂了的逐条看：
   - 脚本没写对 → 改脚本，不算判定
   - 页面上真没了 → 走不通，判「说不准」，见「走不通必须上报」
   - 断言没过 → 照 `缺陷门槛.md` 过两关。过了 → 写问题单，脚本标 `问题-xx 待确认`，进审核表；
     没过 → 判「说不准」，报告里一句话，**不写问题单**
5. **跑稳**：再连跑两次，三次一样，「脚本」列写 `已存`
6. **落文件**：覆盖表、用例清单（「最近判定」「脚本」两列）这一个模块的都写好，再开始下一个模块

基线是照现状写的，第 4 步不会因为它挂，也不会因为它报任何东西。

## 覆盖表 `地图/覆盖表.md`

**这张表是全项目覆盖的标准**：每一格要么扫过了，要么写着为什么没扫。
也是**下一个对话的记忆** —— 新开的对话读它就知道扫到哪了，不靠聊天记录。

```markdown
# 覆盖表

模块 13 个：扫完 3 个、扫了一半 1 个、没扫 9 个。核心流程：建商品 → 建批次 → 发标签 → 扫码（已扫完）

| 模块 | 页面 | 功能点 | 类型 | 扫了没 | 用例 |
| --- | --- | --- | --- | --- | --- |
| 商品库 | [商品列表](企业端/商品库.yaml) | 搜索 | 列表 | 扫过 · 10-26 | [商品-01](../用例/商品库.yaml)、[商品-02](../用例/商品库.yaml) |
| 商品库 | 商品列表 | 翻页 | 列表 | 没扫：只有 1 条数据，翻不了页 | |
| 商品库 | 新建商品 | 新建 | 表单 | 读了字段没提交：会占免费额度 | 没出：没提交过，不知道保存后会怎样 |
| 合格证 | 开具合格证 | 开具 | 表单 | 没扫：禁点清单命中 | |
| 系统设置 | — | — | — | 没扫：只读了骨架 | |
```

## 每个页面扫到什么程度

| 类型 | 扫到哪 |
| --- | --- |
| 列表 | 搜索、筛选、翻页、排序、看详情 —— **只读的都做** |
| 表单 | 打开，读字段：哪些必填、格式提示、有哪些选项。**不提交**，除非下面那条允许 |
| 弹层、抽屉 | 打开读完再关掉。**弹层挂在页面主体外面，地址也不变**，读整页 |
| 删除、作废、签发 | 记录入口在，不点 |

脚本能做的事**不超过扫的时候能做的事**：扫的时候没提交的表单，脚本里也不提交；禁点的，脚本里也不点。

**要造数据才能扫下去的**（核心流程常常要）：只在 `项目适配.md` 写明了"测试账号可以造数据"、
而且额度够的时候做，数据名字带 `QA测试`，做了几条写进副作用记录。造数据的用例范围标 `全量`。
不满足就扫到提交按钮前停下，覆盖表写「读了字段没提交：原因」，交给用户定。

## 控制成本

**token 的大头不在看页面，在对话太长。** 一屏只取可交互元素约 60 token，
但对话每多一轮，前面的全部内容都要再读一遍。所以：

- **全部扫完时，一个模块一个对话。** 扫完一个模块，更新覆盖表，告诉用户：
  「商品库扫完了，建议开一个新对话打 `/qa-测` 说继续扫没扫的」。进度在覆盖表里，不会丢
- **一次读一批，少来回。** 一个模块的几个页面，能用脚本一次读完、把读到的存成文件，就不要一页聊一轮
- **通过的不再看。** 脚本跑过了就是过了，不为它再打开页面
- 侧边栏、顶栏这种每页都一样的东西，**读一次就够**，后面的页面说"同上"

## 接着扫

覆盖表已经有了：

| 用户说 | 扫什么 |
| --- | --- |
| 「继续扫没扫的」 | 覆盖表里「没扫」和「扫了一半」的，按表里的顺序 |
| 「扫商品库」 | 只扫这个模块 |
| 「全部扫完」 | 所有没扫的，一个模块一个对话（见上） |
| 「页面改版了，重扫 XX」 | 重扫这个模块：先跑一遍它已有的脚本，挂的看是改版还是 bug；改版的只改 `绑定/`，`用例/` 不动；新出来的功能点补用例和脚本 |

老项目覆盖表里写「走过」的，当成「扫过」，但那时候没写脚本：用例清单「脚本」列是 `未存`、`草稿` 的，接着扫时顺手照 `写脚本.md` 补上。

## 边扫边说

每读完一个页面、每跑完一个模块，报一句：扫到哪了、写了几条、跑的结果（几条过、几条没变、几条挂了、挂的是什么）。
**不要闷头扫完一个模块才开口**——用户不知道你在干什么，就没法叫停。

## 硬约束

1. **读界面结构，不要截图。** 三个端都一样，只是读的东西不同（具体命令在平台文件里）：

   | 端 | 读什么 |
   | --- | --- |
   | Web | 无障碍树，只取可交互元素。同一屏实测：截图约 1700 token，无障碍树全量 470，只取可交互元素 **60** |
   | 安卓 | uiautomator 导出的界面树，只取有 text 或 content-desc 的节点，量级和 Web 相当 |
   | 小程序 | 当前页面的路径 + 页面数据 + 元素，**页面数据是别的端没有的**，断言时优先用它 |

   **截图是最后手段**，只在"样式错位、图片没加载、颜色不对"这类非看图不可时用。

   **读不到不等于不存在**：安卓上防截屏的页面截图是全黑或 0 字节、模拟器卡死时截图全白，
   这都不是 App 的 bug，判断方法见 `平台-安卓.md`。

2. **命中禁点清单的元素：记录它存在，不要点**，脚本里也不准点。

3. **限深**：一个页面往里最深 5 层。遇到记过的页面就回退。
   不限总步数 —— 全覆盖本来就要走很多步，靠「一个模块一个对话」控制，不靠砍步数

4. **不要乱造数据。** 空列表页如实记成 `空状态，没走进去`。
   要造数据才能扫的，按上面「每个页面扫到什么程度」那条办

5. **要输入时只用 `测试数据/固定数据.json` 里的值**，不许自己编。

6. **有多个系统时，一个系统一个系统地扫**，写进 `地图/<系统>/`，
   各自对照 `02-禁点清单.md` 里该系统那一段。不要从一个系统顺着链接走进另一个系统。

7. **每一步操作之前，先确认当前在哪一页。** 点之前先读一眼当前页面的标题或地址，
   不要假设"上一步点完就一定到了那一页"。假设错了就会点空，然后开始怀疑页面有问题。

8. **看着不对劲，不另记"怀疑"，写成断言让脚本判。** 能指出原文或通用规律的，写成用例；
   指不出的，就是基线，照现状写。**不另外去核实、不去两个端对比、不为它去数数字** —— 那是脚本的事。
   **例外**：为了知道某个操作会不会留痕迹（比如预览算不算一次扫码），可以量一次，这关系到后面安不安全，量了写进副作用记录

9. **不汇总别人的个人信息。** 页面上看到别人的 IP、手机号、邮箱：记下"这个页面显示了 XX"，
   **不要去收集、统计、导出这些值**，哪怕是为了证明这是个 bug。

## 扫完要证明自己改了什么、没改什么

**扫之前记下几个关键数字（列表条数、额度用量），扫完再数一遍，把两次的数字都报出来。**
没造数据的，两次应该一样；造了数据的，差几条就该是你造的那几条（脚本跑了三次的，算上这三次）。

## 输出

### `地图/<系统>/<模块>.yaml`

文件头必须写明**用哪个账号、什么环境、哪天**扫的。
**不同账号看到的入口不一样** —— 同一个站，游客能看到的菜单，专用账号可能没有。

```yaml
模块: 优惠券
时间: 2026-10-26T14:30
环境: 生产 https://xxx.com
角色: 企业用户（测试数据/登录态/企业用户.json，显示名「沫」）
起点: /dashboard

页面:
  个人中心:
    路径: /profile
    可点的:
      - { 名称: 卡券包,   类型: link }
      - { 名称: 注销账户, 类型: button, 状态: 禁点清单命中·没点 }
    跳转:
      卡券包: 优惠券列表

没走到的:
  - 页面: 优惠券详情
    原因: 要点「立即使用」，会进下单流程，超出本模块范围
```

**「路径」这一栏按端填**：Web 填 URL 路径（`/profile`）；安卓填 Activity 加界面标题；
小程序填页面路径加参数（`pages/order/detail?id=xxx`）。格式见各自的平台文件。

### `绑定/`

扫的过程中把"这个页面从哪进、这个弹层怎么打开、这个按钮叫什么"记进 `绑定/`。
这一层是**业务语言到页面位置的对照**，脚本照它找元素，界面改了只动它。

### `用例/`、`脚本/`、`用例清单.md`

照 `写用例.md` 和 `写脚本.md`。

### 有问题的：问题单、审核表

过了缺陷门槛的，问题单写进 `报告/<日期>/疑似问题/问题-xx.md`，格式见 `回归.md` 「判定必须带依据」，
证据放 `报告/<日期>/证据/`。编号接着整个项目往下排。
再在 `用例/审核表.md` 的「是不是 bug」那一段加一行，照 `qa-审完了/审核表.md`。

**一条都没有，就不写报告、不写审核表。** 扫的结果在用例清单里，用不着另一份报告。

## 必须停下来报告

- 出现禁点清单之外、但明显危险的操作（付款、发送、注销、删除全部）
- 连续 3 步没发现新页面
- 跳回登录页 / App 被登出 / 小程序要求重新授权 —— **别去手动登录**，说明登录态失效了，停下来说
- 页面崩溃或白屏 —— 这是硬规律，照缺陷门槛写问题单，继续扫

## 走不通必须上报，不准自己换路

计划走 A，A 走不通时：

```yaml
走不通:
  - 计划: 从「个人中心」点「卡券包」
    实际: 「卡券包」不存在
    看到的: [订单, 设置, 帮助]
```

**静默绕过是这套流程里最危险的行为。走不通本身就是信息。** 脚本里也一样：不准换条路让它变绿。

## 收尾额外要说

- 「扫了 N 个模块，存了 M 条脚本：验过对错的 A 条（有原文或通用规律）、只防变化的 B 条（基线）。要你定的 C 条。」
- **基线是什么意思，第一次扫的时候说一遍**：「这 B 条没有文档能说明对不对，我按现在的样子存了，以后变了会提醒你。
  系统本来就错、又没有文档写过的地方，这样抓不到；你以后给我 PRD、或者在审核表里说一句，它们就能变成真规则」
- 覆盖到哪了，没扫完的以后怎么接着扫（给出那句话）
- 没存成脚本的几条、为什么；扫之前扫之后的关键数字一不一样
- 以后怎么跑：打 `/qa-测` 就会回归这些；想自己跑，给出那条命令（Playwright 是 `npx playwright test`，按编号 `-g "批次-01"`）

## 收尾前自己查

- `地图/覆盖表.md`：每一格是不是都有状态，「没扫」的有没有原因，扫过的「用例」列有没有填
- `用例清单.md`：这次写的每条，「脚本」列都有值，「最近判定」都有值
- 每条问题单都能指出违反了哪条原文或哪条硬规律；**基线挂了的、说不出原文的，一条都没写成问题单**
- 全文搜一下选择器：Web 搜 `div`、`.`、`//`；安卓搜 `resource-id`、`com.` 开头的包名、写死的坐标；
  小程序搜 `.` 开头的 class。**这些只能待在 `绑定/` 和 `脚本/`，地图和用例里一个都不该有**
- 已存的脚本连跑三次结果一样

## 老项目

**没有覆盖表**：按已有的地图补一张，走过的标「扫过」，地图里「没走到的」照抄原因，
菜单里有、地图里没有的标「没扫」。补完告诉用户，并问他这次要接着扫哪块。

**老地图里有 `notes` 记的怀疑**：不用单独处理。扫到那个页面时，能写成断言的写成用例，脚本会判；写不成的丢掉。
