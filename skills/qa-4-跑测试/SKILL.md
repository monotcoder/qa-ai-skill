# 第 4 步 · 跑一轮，出报告

## 先问清楚这轮跑什么

用户说的话对应跑什么：

| 他说 | 跑什么 |
| --- | --- |
| 「跑批次发布」「回归一下批次那块」 | `cases/` 里 `流程: 批次发布` 的全部 |
| 「跑 B-02 到 B-04」 | 这几条 |
| 「全部跑一遍」 | `cases/` 里所有的 |
| 「跑冒烟」「看看页面挂没挂」 | `tests/` 里的冒烟脚本，**不跑业务用例** |
| 没说清楚 | **问一句**，别自己决定。看 `cases/用例清单.md` 报给他有哪些流程 |

开跑前把这轮要跑的**逐条列出来**，让他看一眼再开始。

**`状态: 待实现` 的不跑**（开发阶段照 PRD 先写的用例，功能还没做出来）。
跳过几条要报出来：「这轮跳过 3 条待实现的，功能还没提测」。
把待实现的判成失败，等于天天红，没人再看报告。

## 开始前

1. 读项目根目录的 `项目适配.md`，这个项目的做法和踩过的坑都在里面。
   **没有就当场建一个**：按 `qa-1-建目录` 那个 skill 目录里的 `项目适配模板.md`，
   只建这一个文件，别的不动，建完告诉用户。第一次跑踩的坑最多，没地方写就全丢了。
2. `tests/` 里已经有存好的脚本 → **先跑脚本**。便宜、确定，几十秒出结果。
   再让 AI 跑 `cases/` 里还没存成脚本的用例。
3. 告诉用户：这轮跑哪些、大概多久、**能不能看、怎么看**。

跑的过程中，每跑完一条用例报一句结果。不要闷头跑完才开口。

## 先绑定，再执行

`cases/` 里的步骤是业务语言（"进入购物车"），`maps/` 里是真实路径。
先把两边对上，写进 `bindings/`：

```yaml
"进入购物车": 首页 → 点击"购物车"角标
"选择该券":   提交订单页 → 优惠券行 → 列表中匹配"满100减20"
```

**界面改了只改这一层，`cases/` 一个字都不动。**

按名字找元素**要精确匹配**。大多数工具默认是"包含"：
找「游客登录」会同时匹配到「游客登录体验」，点错了也不报错。

## 判定三档，不是两档

| 判定 | 什么时候用 |
| --- | --- |
| `通过` | 符合预期，**且你能指出依据**。用例的 `预期来源` 是 `AI推测` 的，**不准判通过**（见下） |
| `失败` | 违反了某条明确写下来的规则 |
| **`说不准`** | 规则没覆盖到 / 依据模糊 / 你也不确定 |

> **「说不准」不是失职，是最有价值的输出。硬着头皮下结论才是。**

一轮里 `说不准` 占 10~20% 是健康的。
接近 0 说明在硬判，超过 40% 说明 `cases/` 写得太含糊 —— 两种都要说出来。

## `预期来源` 决定这条最高能判到什么

| `预期来源` | 最高能判 |
| --- | --- |
| `PRD` / `产品说明` / `用户确认` | 通过 |
| **`AI推测`** | **最高只能判「说不准」** |
| **`基线`**（照上一版行为存的） | 通过只代表**没变**，不代表对。报告里要写明 |
| **`冲突待裁决`**（PRD 跟成品对不上） | **只能判「说不准」**，把两边差异列出来，人来裁决 |

AI 猜的预期，跟系统现在的行为一对，当然是"符合"——
**这是拿系统证明系统，bug 会被原样判成通过。**

遇到这种，报告里写：「B-01 行为和预期一致，但这条预期是 AI 猜的，你确认后才算通过」。

## 判定必须带依据

不要只给结论。**人 review 的是依据，不是结论** —— 依据对不对一眼看得出来，结论对不对看不出来。

```json
{
  "id": "C-07",
  "规则": "PRD 3.2 · 订单满 100 元才能用满减券",
  "步骤": ["进入购物车（99 元）", "点去结算", "选「满100减20」"],
  "预期": "券置灰，提示还差 1 元",
  "实际": "券可选中，点击后弹「系统错误」",
  "判定": "失败",
  "依据": "PRD 3.2 写了门槛校验应在选择时拦截，这里没拦截且报了未定义错误",
  "证据": {
    "aria快照": "reports/2026-09-20/evidence/C-07.aria.yaml",
    "控制台": "TypeError: Cannot read properties of undefined (reading 'threshold')",
    "网络": "POST /api/coupon/apply → 500",
    "trace": "reports/2026-09-20/evidence/C-07.trace.zip"
  }
}
```

## 下结论之前，先核实一次

AI 最容易犯的不是漏报，是**误报**。判「失败」之前，换一种方式再确认一次：

| 看到的 | 先查什么 |
| --- | --- |
| 两个数字对不上 | 标签是不是同一个口径（累计 vs 本月、全部 vs 已发布） |
| 界面上一列是空的 | **看接口有没有返回这个数据**：有 → 前端没显示；没有 → 后端没给。这决定了该找谁修 |
| 读取工具说某个元素没名字、不存在 | 直接看元素里的文字，读取工具的显示模式可能不全 |
| 时红时绿 | 先怀疑并发和等待，不要先怀疑被测系统 |

核实后发现是误报的，**不删，写进报告的「核对后撤回的」**。
用户看到你撤回过什么，才敢信你留下的。

**不汇总别人的个人信息**：页面上看到别人的 IP、手机号、邮箱，记下"显示了"就行，
不要去收集、统计这些值来证明是 bug。证据里也不要写这些值。

## 通用巡检（不需要 PRD，每轮都跑）

在走过的每个页面上验：

```
- 没有崩溃、白屏、错误页
- 控制台没有 error，网络没有 5xx
- 界面上不出现 undefined / null / NaN / [object Object]
- 返回键能回上一页，不卡死
- 关键数字自洽：总额 = 各分项之和
- 任意输入框塞 500 字符不崩
```

这层最划算：**答案不依赖需求，你自己就能判**，而且人最不爱干。

## ⚠️ 走不通必须上报，不准自己换路

用例第 3 步的按钮点不到时：

```json
{
  "判定": "说不准",
  "走不通": {
    "计划": "点商品详情页的「加入购物车」",
    "实际": "该按钮不存在",
    "看到的": ["立即购买", "收藏", "分享"],
    "我没做的事": "没有改用列表页的快捷加购"
  }
}
```

**你绕过去了，bug 就被埋了。** 这是整套流程里最容易犯、代价最大的错。

## 跨系统用例（`cases/` 里有 `谁:` 或 `对账:` 时）

**多个账号**：同一个浏览器里，一个站点只能登一个账号。
每个角色开一个互相隔离的浏览器环境，各带各的登录状态，不要在一个里面退出再登。

**等待**：轮询到条件成立，不准固定 sleep。超过用例里写的时限就判失败 ——
时限到不了本身就是 bug，不是"环境慢"。

**上下游：流程走完不算通过，字段对账全部相等才算。**
按 `bindings/` 的「ID对照」串起链路，按「数据位置」逐字段取值比对。

**挂了必须报出断在哪一跳**，不能笼统说失败：

```json
{
  "判定": "失败",
  "断点": "第 2 跳：订单系统 → 财务系统",
  "已确认": "订单系统下单成功，orderNo 20260921-0043，接口 200",
  "未发生": "财务系统 60 秒内查不到 outNo=20260921-0043",
  "还没查的": "消息有没有投递 / 是不是被过滤条件挡了"
}
```

跨系统的 `说不准` 比例会明显偏高 —— 边界上谁的锅本来就不清楚。
这是正常形态，在报告里说明，不要为了压比例硬判。

## 每条都要能回放

跑的时候**把过程录下来**（Playwright 是 trace，其他工具找等价的）。
用户不信哪一条，点开就能一步步看你到底点了什么、当时页面长什么样。

**这是「通过」能不能被信任的关键。** 没有回放，「通过」就只是你的一句话。
报告里每条都写上回放文件在哪、怎么打开。

## 输出

```
reports/2026-09-20/
├─ report.md       # 人看的汇总
├─ findings/       # 疑似问题，等人确认 ← 失败和说不准都落这儿
│  └─ F-01.json
└─ evidence/       # 回放文件、快照、控制台
```

`findings/` 里的**还不是 bug，是疑似**。人确认后才 `/qa-6-提bug`。

判了「通过」的，可以用 `/qa-5-存成脚本` 存下来，以后每次发版跑脚本就行。

## 报告第一段先写「这轮没验什么」

不是写在结尾，**写在最前面**。用户看到「通过」两个字，默认会以为功能测过了。

```markdown
## 这轮验了什么

- 跑的是：批次发布流程的 B-01 ~ B-05（5 条）
- **没验**：合格证、标签、统计报表；这 5 条里有 2 条的预期是 AI 猜的，等你确认

## 结果
...
```

只跑了冒烟的时候说得更直白：**「这轮只验证了页面能打开，功能一个都没测」**。

报告结尾再附一句：

> 绿灯 ≠ 能发版，红灯 = 一定不能发版。
> 没覆盖的部分见 `calibration/known-bugs.yaml` 的缺口清单。

## 收尾前：检查要不要写进 `项目适配.md`

逐条过一遍。**有任何一条，就必须写进「踩过的坑」**（做法 / 为什么 / 日期）：

- 换过等待方式（比如这个站不能等网络完全安静）
- 调整过并发（比如只能一个浏览器跑）
- 登录方式跟记录的不一样，或者多用了一个账号
- 为了跑通，改过配置文件
- 撤回过误报，而误报的原因是这个项目特有的
- 某种元素只能用特殊的方式找到

收尾汇报里**必须有一行**：`项目适配.md：补了 N 条（逐条列出）` 或 `项目适配.md：这次没补`。
不能只靠自觉——写没写，要让用户一眼看得到。

## 做完就停

把报告交给用户：几条通过、几条失败、几条说不准、撤回了几条。
**然后停下，等他逐条确认。** 不要自己去提 bug，也不要自己去存脚本。

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。
