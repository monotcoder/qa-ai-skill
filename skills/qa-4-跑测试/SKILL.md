# 第 4 步 · 跑一轮，出报告

## 开口第一行：报版本

开始做之前，**第一行单独写**：

```
QA 流水线 v1.4.0 · qa-4-跑测试
```

就这一行，不加别的话，像软件标题栏那样。直接写出来，不用放进代码块。
版本号就是这个文件开头那行注释里的 `version`，**不要去磁盘上读文件来报** ——
你报的必须是你现在加载的这一份。学员出问题时，作者靠这一行知道他跑的是哪一版。

接着顺手比一下（找得到就比，找不到就跳过，不要卡住）：

- skill 目录里 `qa-更新/版本.json` 的版本比你报的新 → 这个对话加载的是旧版。
  告诉用户「skill 已经更新了，但这个对话还在用旧版，请重启 AI 工具或者开一个新对话，再打这个命令」。
  他说「继续」，就照你现在这一版接着做，不要拦着
- 项目里 `.qa-ai.json` 的版本比你报的新 → 这个项目是更新的版本建的，提醒他先打 `/qa-更新`

这一步新写或改过的文档（地图、覆盖表、用例清单、报告、问题单、变更单），标题下面写一行
`生成：QA 流水线 v1.4.0 · qa-4-跑测试 · <日期>`。改已有的文档，把这一行改成这一次的。

## 先问清楚这轮跑什么

用户说的话对应跑什么：

| 他说 | 跑什么 |
| --- | --- |
| 「跑批次发布」「回归一下批次那块」 | `用例/` 里 `流程: 批次发布` 的全部 |
| 「跑批次-02 到批次-04」 | 这几条 |
| 「全部跑一遍」 | `用例/` 里所有的 |
| 「跑冒烟」 | `用例/` 里 `范围: 冒烟` 的那批 + `脚本/` 里存好的。**这批不能有累积、不可逆、对外可见的副作用**；计数类（扫码量 +1）可以，记进副作用记录 |
| 「跑全量」 | 全部，包括会留痕迹的 |
| 没说清楚 | **问一句**，别自己决定。看 `用例/用例清单.md` 报给他有哪些流程 |

开跑前把这轮要跑的**逐条列出来**，让他看一眼再开始。

**这几种不跑**，跳过几条要报出来，别判成失败：

- `状态: 待实现`：功能还没做出来（开发阶段照 PRD 先写的）
- `状态: 待数据`：缺前置数据
- `范围: 要用户准备`：**用户没明说"可以跑"就不跑**，更不要自己删数据去腾位置

把这些判成失败，等于天天红，没人再看报告。

## 跑之前先做环境体检

下面任何一项不对，**全部用例都会红，而且红得跟被测系统毫无关系**。先查，不对就停下来报告：

| 查什么 | 怎么查 |
| --- | --- |
| 登录态还有效 | 看过期时间，或者拿它打开一次首页看显示的是谁 |
| 要用到的每个域名的证书没过期 | 读证书的有效期，不要靠"打开页面没报错"判断 |
| 网络能直连 | 本机开了代理的，代理可能掐断某些域名的连接。**命令行工具和浏览器走不走代理不一样**，一个通一个不通时，先怀疑代理 |

体检发现的问题分两种：

- **环境的问题**（登录态过期、本机代理）：不是 bug，请用户处理，处理完再跑
- **被测系统的问题**（证书过期、域名打不开）：**这是线上事故，直接报，标紧急**。
  不要忽略证书错误硬打开，也不要换个域名绕过去 —— 绕过去了，报告里是"通过"，用户那边是打不开

## 开始前

1. 读项目根目录的 `项目适配.md`，这个项目的做法和踩过的坑都在里面。
   **没有就当场建一个**：按 `qa-1-建目录` 那个 skill 目录里的 `项目适配模板.md`，
   只建这一个文件，别的不动，建完告诉用户。第一次跑踩的坑最多，没地方写就全丢了。
2. `脚本/` 里已经有存好的脚本 → **先跑脚本**。便宜、确定，几十秒出结果。
   再让 AI 跑 `用例/` 里还没存成脚本的用例（看 `用例清单.md` 的「脚本」列）。
3. 告诉用户：这轮跑哪些、大概多久、**能不能看、怎么看**。

跑的过程中，每跑完一条用例报一句结果。不要闷头跑完才开口。

## 先绑定，再执行

`用例/` 里的步骤是业务语言（"进入购物车"），`地图/` 里是真实路径。
先把两边对上，写进 `绑定/`：

```yaml
"进入购物车": 首页 → 点击"购物车"角标
"选择该券":   提交订单页 → 优惠券行 → 列表中匹配"满100减20"
```

**界面改了只改这一层，`用例/` 一个字都不动。**

按名字找元素**要精确匹配**。大多数工具默认是"包含"：
找「游客登录」会同时匹配到「游客登录体验」，点错了也不报错。

## 跑脚本时，已知失败的那几条要多看一眼

脚本里标了「已知失败」的（`test.fail`，标记里写着 `已知-xx`），结果有三种：

| 结果 | 说明什么 | 怎么报 |
| --- | --- | --- |
| 失败，**失败在 bug 那一句断言上** | bug 还在 | 「已知-05 还没修」，不算新问题 |
| 失败，**失败在别处**（比如前提断言、点不到按钮） | 出了新情况，被已知失败的标记吞掉了 | **当新问题报**，判「说不准」，写明失败在哪一行 |
| **本该失败却通过了** | bug 可能修好了 | 「已知-05 可能修好了」，AI 照用例再走一遍核实 |

失败在哪一行，读工具的结果文件就知道（Playwright 的 json 结果里有 `errorLocation`），不用截图。

核实修好了：跟用户说一声，他点头后去掉脚本里的已知失败标记，
`用例清单.md` 的「脚本」列改成 `已存`，`校准/已知bug.md` 里那条标上「已修 · 日期」。

## 跑完回写用例清单

每跑完一条，改 `用例/用例清单.md` 的「最近判定」列：`通过 · 10-12`、`失败 · 已知-05`、`说不准 · 接口层没验`。
**这一列和「脚本」列是下一个对话的记忆**：新开的对话只读这张表，就知道哪些该提 bug、哪些该存脚本。

## 判定三档，不是两档

| 判定 | 什么时候用 |
| --- | --- |
| `通过` | 符合预期，**且你能指出依据**。用例的 `预期来源` 是 `AI推测` 的，**不准判通过**（见下） |
| `失败` | 违反了某条明确写下来的规则 |
| **`说不准`** | 规则没覆盖到 / 依据模糊 / 你也不确定 |

> **「说不准」不是失职，是最有价值的输出。硬着头皮下结论才是。**

一轮里 `说不准` 占 10~20% 是健康的。
接近 0 说明在硬判，超过 40% 说明 `用例/` 写得太含糊 —— 两种都要说出来。

**没有「部分通过」这一档。** 一条用例只验了一半（比如「看不到、改不了」只验了「看不到」）：
验了的那半是通过，没验的那半就是 `说不准`，整条判 `说不准`，写明哪一半没验、为什么。
合计里不准把它算进通过。这种用例下次 `/qa-3-出用例` 时拆成两条，各判各的。

## `预期来源` 决定这条最高能判到什么

| `预期来源` | 最高能判 |
| --- | --- |
| `PRD` / `产品说明` / `通用规律` / `用户确认` | 通过 |
| **`AI推测`** | **最高只能判「说不准」** |
| **`基线`**（照上一版行为存的） | 通过只代表**没变**，不代表对。报告里要写明 |
| **`冲突待裁决`**（PRD 跟成品对不上） | **只能判「说不准」**，把两边差异列出来，人来裁决 |

AI 猜的预期，跟系统现在的行为一对，当然是"符合"——
**这是拿系统证明系统，bug 会被原样判成通过。**

遇到这种，报告里写：「批次-01 行为和预期一致，但这条预期是 AI 猜的，你确认后才算通过」。

## 判定必须带依据

不要只给结论。**人 review 的是依据，不是结论** —— 依据对不对一眼看得出来，结论对不对看不出来。

失败和说不准的，每条写一份问题单 `疑似问题/问题-xx.md`。**编号接着整个项目往下排**：
先看所有 `报告/*/疑似问题/` 里最大的号，从下一个开始，换一天不从 01 重来。

问题单**用 Markdown，不用 JSON** ——
人要点开来读，JSON 满屏引号和括号没人看得下去：

```markdown
# 问题-01 · 满100减20券在99元订单上可选中，点击后报系统错误

| 项 | 内容 |
| --- | --- |
| 用例 | [优惠券-07](../../../用例/优惠券.yaml) |
| 规则 | PRD 3.2 · 订单满 100 元才能用满减券 |
| 判定 | 失败 |
| 平台 | 状态：待确认 · 单号：无 |

## 步骤
1. 进入购物车（99 元）
2. 点去结算
3. 选「满100减20」

## 预期
券置灰，提示还差 1 元

## 实际
券可选中，点击后弹「系统错误」

## 依据
PRD 3.2 写了门槛校验应在选择时拦截，这里没拦截且报了未定义错误

## 证据
- 回放：[优惠券-07-回放.zip](../证据/优惠券-07-回放.zip)（`npx playwright show-trace 报告/2026-09-20/证据/优惠券-07-回放.zip`）
- 页面结构：[优惠券-07-页面结构.yaml](../证据/优惠券-07-页面结构.yaml)
- 控制台：`TypeError: Cannot read properties of undefined (reading 'threshold')`
- 网络：`POST /api/coupon/apply → 500`
```

下面「走不通」「断点」那几段，也是写进问题单里的小节。

## 下结论之前，先核实一次

AI 最容易犯的不是漏报，是**误报**。判「失败」之前，换一种方式再确认一次：

| 看到的 | 先查什么 |
| --- | --- |
| 两个数字对不上 | 标签是不是同一个口径（累计 vs 本月、全部 vs 已发布） |
| 界面上一列是空的 | **看接口有没有返回这个数据**：有 → 前端没显示；没有 → 后端没给。这决定了该找谁修 |
| 读取工具说某个元素没名字、不存在 | 直接看元素里的文字，读取工具的显示模式可能不全 |
| 时红时绿 | 先怀疑并发和等待，不要先怀疑被测系统 |

核实后发现是误报的，**不删，写进报告的「核对后撤回的」**。
用户看到你撤回过什么，才敢信你留下的。

**不汇总别人的个人信息**：页面上看到别人的 IP、手机号、邮箱，记下"显示了"就行，
不要去收集、统计这些值来证明是 bug。证据里也不要写这些值。

## 通用巡检（不需要 PRD，每轮都跑）

在走过的每个页面上验：

```
- 没有崩溃、白屏、错误页
- 控制台没有 error，网络没有 5xx
- 界面上不出现 undefined / null / NaN / [object Object]
- 返回键能回上一页，不卡死
- 关键数字自洽：总额 = 各分项之和
- 任意输入框塞 500 字符不崩
```

这层最划算：**答案不依赖需求，你自己就能判**，而且人最不爱干。

## 走不通必须上报，不准自己换路

用例第 3 步的按钮点不到时：

```json
{
  "判定": "说不准",
  "走不通": {
    "计划": "点商品详情页的「加入购物车」",
    "实际": "该按钮不存在",
    "看到的": ["立即购买", "收藏", "分享"],
    "我没做的事": "没有改用列表页的快捷加购"
  }
}
```

**你绕过去了，bug 就被埋了。** 这是整套流程里最容易犯、代价最大的错。

## 跨系统用例（`用例/` 里有 `谁:` 或 `对账:` 时）

**多个账号**：同一个浏览器里，一个站点只能登一个账号。
每个角色开一个互相隔离的浏览器环境，各带各的登录状态，不要在一个里面退出再登。

**等待**：轮询到条件成立，不准固定 sleep。超过用例里写的时限就判失败 ——
时限到不了本身就是 bug，不是"环境慢"。

**上下游：流程走完不算通过，字段对账全部相等才算。**
按 `绑定/` 的「ID对照」串起链路，按「数据位置」逐字段取值比对。

**挂了必须报出断在哪一跳**，不能笼统说失败：

```json
{
  "判定": "失败",
  "断点": "第 2 跳：订单系统 → 财务系统",
  "已确认": "订单系统下单成功，orderNo 20260921-0043，接口 200",
  "未发生": "财务系统 60 秒内查不到 outNo=20260921-0043",
  "还没查的": "消息有没有投递 / 是不是被过滤条件挡了"
}
```

跨系统的 `说不准` 比例会明显偏高 —— 边界上谁的锅本来就不清楚。
这是正常形态，在报告里说明，不要为了压比例硬判。

## 每条都要能回放，但只留该留的

跑的时候**每条都录**（Playwright 是 trace，其他工具找等价的）。用户不信哪一条，点开就能一步步看你点了什么。

录了不等于都要留下来。一条回放几百 KB 到一两 MB，一轮十几条就是十几 MB，一个月下来项目里全是 zip：

| 这条 | 回放放哪 |
| --- | --- |
| 失败、说不准 | **放进 `报告/<日期>/证据/`，长期留**。要进问题单、要给开发看 |
| 已知 bug 这轮没复现（可能修好了） | 同上，要拿去关单 |
| 通过 | **不放进 `证据/`**。留在工具自己的输出目录里（见 `项目适配.md`，一般是 `.playwright/`），下一轮会被覆盖。报告里不给链接，结尾写一句「通过的回放在 XX，下一轮会被覆盖，要长期留就说一声」 |

**解压回放来看的，解到临时目录，看完删掉**，不要解在 `证据/` 里 —— 解开就是几十个零碎文件。

├─ 疑似问题/       # 等人确认 ← 失败和说不准都落这儿

判了「通过」的，可以用 `/qa-6-存成脚本` 存下来，以后每次发版跑脚本就行。

## 报告：先结论，正常的一行带过

报告是给人看的，**打开第一屏就要知道三件事：能不能发版、有几个新问题、要他做什么**。
细节不是不要，是放对地方：每条失败的步骤、接口、元素原文写在问题单里，报告里一句话加链接。

**整份报告控制在 40 行左右。** 写长了，要紧的那两行会被埋掉。照这个样子：

```markdown
# 冒烟测试报告 · 2026-10-15

生成：QA 流水线 v<版本号> · qa-4-跑测试 · <日期>

**17 条：通过 13、失败 4、说不准 0。新问题 2 条等你确认，已知 bug 2 条还没修。不能发版。**

**没验什么**：新建、发布这些写操作一条没跑；表单校验、筛选、翻页、导出没有用例。
全项目 12 个模块，有用例的 4 个，见 [覆盖表](../../地图/覆盖表.md)。

## 要你定的

- [问题-01](疑似问题/问题-01.md) 标签按完整商品名搜不到：是不是 bug？
- [问题-03](疑似问题/问题-03.md) 商品状态列叫「已上架」，筛选里叫「已发布」：是不是 bug？

## 失败和说不准

| 编号 | 判定 | 一句话 | 该找谁 |
| --- | --- | --- | --- |
| [标签-02](../../用例/标签管理.yaml) | 失败 · [问题-01](疑似问题/问题-01.md) | 搜完整商品名 0 条，接口自己返回空 | 后端 |
| [标签-04](../../用例/标签管理.yaml) | 失败 · [已知-02](../../校准/已知bug.md) | 还没修 | — |

## 通过（13 条）

| 编号 | 依据 |
| --- | --- |
| [商品-01](../../用例/商品库.yaml) | 搜商品名，只剩这一条 |
| [扫码-02](../../用例/扫码追溯.yaml) | 打开一次，累计 6 → 7，再等 5 秒没多算 |

## 其他

- 环境体检：正常
- 已知 bug：2 条都抓到了（已知-01、已知-02）
- 通用巡检：没发现问题。没做：返回键、长字符串
- 副作用：扫码页打开 1 次，累计 6 → 7
- 核对后撤回：第一遍等待太松读错了条数，那一遍全部作废，报告里是重跑的结果

> 绿灯 ≠ 能发版，红灯 = 一定不能发版。通过的回放在 `.playwright/`，下一轮会被覆盖。
```

几条规矩：

- **第一行就是结论**，不要先铺垫环境、范围。「没验什么」紧跟在结论后面，不准挪到结尾：用户看到「通过」两个字，默认会以为功能测过了。
  只跑了冒烟的，说得更直白：**「这轮只验证了页面能打开，功能一个都没测」**
- **依据一句话**，写看到了什么（「只剩这一条」「6 → 7」），不写接口路径、等待写法、元素属性。那些要么进问题单，要么不写
- **正常的一行带过**：环境体检、已知 bug、巡检、副作用，没事就各一行；有事才展开成表
- **不重复**：结论那一行已经有合计了，不要再出一张合计表；回放怎么打开写在问题单里，报告里不再教一遍
- 「说不准」接近 0 或超过四成的，在结论下面加**一句**为什么，不要写成一段
- 「核对后撤回的」一定要有（有撤回才写），一条一句。用户看到你撤回过什么，才敢信你留下的

## 副作用算没算，量出来，别猜

做了一个可能会计数的操作（打开扫码地址、看一篇文章），**不知道算不算一次的，跑前跑后各读一次那个数**，
报告里写实数：「扫码量 12 → 13」或「没变，草稿不计数」。
不准写「如果草稿也计数的话」这种话 —— 你能量，就不该让用户去猜。
量的时候要多开一个页面、多登一个账号的，照常做，但这次读法和多花的 token 一并写进收尾。
量出来的结论（什么计数、什么不计）写进 `项目适配.md`，下次不用再量。

## 收尾前：检查要不要写进 `项目适配.md`

逐条过一遍。**有任何一条，就必须写进「踩过的坑」**（做法 / 为什么 / 日期）：

- 换过等待方式（比如这个站不能等网络完全安静）
- 调整过并发（比如只能一个浏览器跑）
- 登录方式跟记录的不一样，或者多用了一个账号
- 为了跑通，改过配置文件
- 撤回过误报，而误报的原因是这个项目特有的
- 某种元素只能用特殊的方式找到

收尾汇报里**必须有一行**：`项目适配.md：补了 N 条（逐条列出）` 或 `项目适配.md：这次没补`。
不能只靠自觉——写没写，要让用户一眼看得到。

## 提到的文件和编号，都写成能点开的链接

谁也记不住 `问题-07`、`已知-05` 底下是什么内容。所以：

- **对话里**：提到文件就写成 `[问题-07](报告/2026-10-10/疑似问题/问题-07.md)`，路径从项目根目录算
- **写进文档里的**（报告、变更单、用例清单、已知 bug、问题单）：每个编号、每个证据文件都写成链接，
  路径从**这份文档所在的目录**算（变更单在 `报告/2026-10-12/` 下，链 10-10 的问题单就写 `../2026-10-10/疑似问题/问题-07.md`）
- 编号链到它的出处：用例 → 那条用例所在的 yaml；问题 → 它的问题单；已知 → `校准/已知bug.md`
- **写完把每个链接对一遍文件在不在**。断掉的链接比没有链接更误导人
- 回放这种点开要下载的，链接旁边照样写上打开它的命令

## 对话长了、被压缩了怎么办

**进度随时落到文件里**：每跑完一条用例，就把判定和依据写进 `报告/<日期>/报告.md`，把「最近判定」写进 `用例清单.md`，不要跑完一轮再一起写。
这样不管是工具自动压缩对话、断网，还是用户中途关掉，都不会白做。

**发现对话被压缩过**（对话开头变成了一段摘要）：**先重读再继续** —— 这个 skill 的说明、
`项目适配.md`、`提示词/02-禁点清单.md`，还有记进度的那个文件。不要凭摘要里的印象往下走，
摘要里不一定还留着禁点清单的每一条。

**这一轮对话已经很长**（走完了一个模块、跑了十几条用例、来回几十轮）：收尾时提醒一句
「下一个命令可以在新对话里打，进度都在文件里」。开新对话比压缩好：压缩留下什么你控制不了，
新对话从文件里读，什么都不会丢。对话不长就不用提。

## 收尾：照这个格式报，一条都不能少

1. **这一步动了哪些文件**：按目录分组，新增还是修改，每个一句话
2. **没动哪些**：列出来
3. **现在去看哪个文件**：指一个具体的
4. **这轮读了几屏、用的哪种读法、大约多少 token**
   token 只能估读页面那一部分，**报的时候说清这不是总数**：每多一轮对话，前面的内容都要重读一遍，
   整个对话的消耗通常是读页面的几十倍，以 AI 工具自己显示的用量为准。有副作用的操作做了几次，也在这一条报
5. `项目适配.md`：补了 N 条（逐条列出）或 这次没补
6. **下一步打哪个命令**

这一步额外要说：几条通过、几条失败、几条说不准、撤回了几条、跳过几条为什么跳过。

**收尾前你自己先把下面这几条查一遍**，在收尾里报结果：每条一句「过了」或「没过：原因」，带上能点开的文件链接，他想抽查点开就能看。**你能查的事不要甩给用户去查**。没过的，能改就先改好再收尾：

- `报告/<日期>/报告.md`：第一行是不是结论，紧跟着是不是「没验什么」；整份是不是 40 行左右，正常的是不是一行带过
- 每条判定后面有没有一句依据；失败的有没有写**该找谁修**
- `证据/` 里：失败和说不准的每条都有回放；**通过的没有放进来**；没有解压出来的零碎文件
- `说不准` 接近 0 或者超过 40%，有没有解释
- **对照 `校准/已知bug.md`：已知的 bug 这轮抓到了没有**。
  抓不到就说明这套东西在装瞎，其他结论一概不能信

**只有他能定的，单独问**：失败和说不准的那几条，是不是 bug。别的不用他查。

**然后停下，等他说哪几条是 bug**（一句话就行：「问题-01 是，问题-03 不是」）。
他答了，**马上写进问题单**：是 bug 的，「平台」那一行改成 `待新建`；不是的，写「用户确认不是 bug · <日期> · 原因」，
是用例预期错了的顺手标出来。这样新开的对话打 `/qa-5-提bug`，不用再问他一遍。 不要自己去提 bug，也不要自己去存脚本。

下一步按这轮的结果说，**两件事都有就都说，提 bug 排前面**（bug 有时效，存脚本没有）：

| 这轮有 | 下一步 |
| --- | --- |
| 失败或说不准，等他确认 | `/qa-5-提bug` |
| 通过了、「脚本」列还是未存的 | `/qa-6-存成脚本`，现在做或者过几天做都行，状态在文件里 |
| 已知 bug 可能修好了 | 先核实，再 `/qa-5-提bug` 出变更单（平台上该关单了），然后 `/qa-6-存成脚本` 去掉已知失败标记 |
| 都没有 | 什么都不用做，下次提测再 `/qa-4-跑测试` |
| 覆盖表里还有没走的模块 | 不管上面是哪种，都提一句：「还有 N 个模块没覆盖，想补就打 `/qa-2-走一遍页面` 说继续走没走的」 |

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。

目录还是英文名的（`cases/`、`maps/` 这些）：按 `qa-1-建目录` 那个 skill 目录里的 `目录对照.md`
找对应的英文目录，照常做，**不要新建中文目录**。做完提一句：「跑一次 `/qa-1-建目录` 可以改成中文目录」。
