# 第 6 步 · 存成脚本

## 开口第一行：报版本

开始做之前，**第一行单独写**：

```
QA 流水线 v1.4.0 · qa-6-存成脚本
```

就这一行，不加别的话，像软件标题栏那样。直接写出来，不用放进代码块。
版本号就是这个文件开头那行注释里的 `version`，**不要去磁盘上读文件来报** ——
你报的必须是你现在加载的这一份。学员出问题时，作者靠这一行知道他跑的是哪一版。

接着顺手比一下（找得到就比，找不到就跳过，不要卡住）：

- skill 目录里 `qa-更新/版本.json` 的版本比你报的新 → 这个对话加载的是旧版。
  告诉用户「skill 已经更新了，但这个对话还在用旧版，请重启 AI 工具或者开一个新对话，再打这个命令」。
  他说「继续」，就照你现在这一版接着做，不要拦着
- 项目里 `.qa-ai.json` 的版本比你报的新 → 这个项目是更新的版本建的，提醒他先打 `/qa-更新`

这一步新写或改过的文档（地图、覆盖表、用例清单、报告、问题单、变更单），标题下面写一行
`生成：QA 流水线 v1.4.0 · qa-6-存成脚本 · <日期>`。改已有的文档，把这一行改成这一次的。

AI 走一遍要花 token、结果每次可能不一样。存成脚本之后：
**以后每次回归先跑脚本，不再让 AI 走**。几十秒跑完，不花 token，结果是确定的。

## 不等，跑完就能存

**不要等 bug 修好再存。** 修 bug 可能要几周，等不到的。
这一步可以紧接着 `/qa-4-跑测试`、`/qa-5-提bug` 做，也可以隔几天在一个全新的对话里做 ——
**该存哪些、存过哪些，全写在文件里，不靠聊天记录。**

## 开始前

1. **先读项目根目录的 `项目适配.md`**。这个项目用什么工具、怎么登录、怎么等、能不能并行，以前踩过的坑都在里面。
   **没有就当场建一个**：按 `qa-1-建目录` 那个 skill 目录里的 `项目适配模板.md`，
   只建这一个文件，别的不动，建完告诉用户。
2. **读 `用例/用例清单.md` 的「最近判定」和「脚本」两列**，这是唯一的依据。
   老清单没有这两列：读 `报告/` 里每条用例最近一次的判定，补上这两列，告诉用户补了
3. 按下面那张表挑出这次要存的，**逐条列给用户，等他点头**

## 哪些存、怎么存

| 最近判定 | 脚本列 | 这次怎么做 |
| --- | --- | --- |
| 通过 | 未存 | **存**，按预期写断言 |
| 失败，用户确认是 bug（有 `已知-xx`） | 未存 | **存成「已知失败」**，见下 |
| 失败，用户还没确认 | 未存 | **不存**。先去 `/qa-5-提bug` 让他确认 |
| 说不准 | 未存 | **不存**。判不准的写成脚本，脚本也判不准 |
| 待数据 / 待实现 / 要用户准备 | — | 不存，脚本列写原因 |
| 任何 | 已存 | 不动。除非用户说这条的预期改了 |

**绝不把 bug 当成预期写进去。** 写进去的永远是**正确的样子**。
页面现在显示了别家的批次，断言写的是「不显示别家批次」，不是「显示了 DEMO-2026-004」。
后一种写法，脚本会一直替 bug 作证。

## 已知失败怎么写

确认是 bug、还没修的，按正确预期写，再标明它现在还不成立：

```ts
test('隔离-02 别家没发布的标签，消费者看不到内容', async ({ page }) => {
  test.fail(true, '已知-05：草稿标签公开可见，等修');
  // ……正常的步骤……
  // 断言写正确的样子：看不到商品、批次
});
```

- 现在跑：失败在意料之中，**不算新问题，不会天天红**
- 修好那天：工具报「本该失败却通过了」—— **这就是 bug 修好的信号**，不用有人记着去回归
- 标记里**必须写已知编号**，跑的人才知道它在等哪个 bug

这种写法有个漏洞：标了已知失败，**因为任何原因失败都算意料之中**，页面改版点不到按钮也会被吞掉。
所以：

- 断言 bug 的那一句前面，**先把前提断言一遍**（页面打开了、看到了一级标题），让别的失败尽早暴露
- 跑的时候 `/qa-4-跑测试` 会核对它**失败在哪一行**（见那一步）

## 存完回写用例清单

每存一条，改 `用例/用例清单.md` 的「脚本」列：

| 写什么 | 什么意思 |
| --- | --- |
| `已存` | 脚本里有，正常断言 |
| `已存 · 等修 已知-05` | 脚本里有，标了已知失败 |
| `未存：<原因>` | 说不准、缺数据、还没确认是 bug…… 写明为什么 |

**这一列就是下一个对话的记忆。** 不写，下次没人知道哪条存过、哪条在等修。

## 工具跟着项目走

- 项目里已经有测试工具 → 用它的
- 没有 → Web 默认 Playwright；App 用项目能跑的宿主侧脚本
- 定下来的写进 `项目适配.md`，下次不再问
- 用的工具没有「已知失败」这种标记的：这条先不存，脚本列写 `未存：等修 已知-xx`，修好了再存

## 写脚本的规矩

**定位**：只用用户看得见的东西——标题、按钮的名字、角色。不用 CSS class、不用 xpath。
按名字找元素**要精确匹配**：大多数工具默认是"包含"，「登录」会同时匹配到「游客登录」。

**等待**：不要写固定秒数。等一个"确实到了"的标志：
- 页面：等标题出现
- 数据：**等业务接口都返回**，不要等"网络完全安静"。有的前端框架（比如 Nuxt）页面出来后还会预加载别的页面的代码，等"安静"会白等，还会被拖到超时

**报错要说人话**：失败时要说清是哪一步、哪个接口、等了多久。
「有接口没返回」没用，「batch/page 等了 4835ms 没返回」才能查。

**测试标题以用例编号开头**：`test('批次-01 新建批次后是草稿状态', ...)`。
这样报告、用例、脚本三处能对上，想单跑一条也只要按编号筛（Playwright 是 `npx playwright test -g "批次-01"`）。

**每条测试独立**：每条从干净的状态开始，不依赖上一条的结果。这样一条挂了不连累下一条。

**有副作用的**（打开一次扫码量 +1）：脚本里也照样会 +1。存之前告诉用户每跑一次会留下什么，
`项目适配.md` 的副作用记录里写明「脚本每跑一次 +N」。

## 存完要跑，跑稳了才算存好

1. **先用一个浏览器跑**：正常的全绿，已知失败的按预期失败
2. **连跑 3 次结果都一样**，才算存好
3. 想并行再试并行。**单个浏览器下得出的"怎么等"的结论，并行时不一定成立** ——
   单跑时等"网络安静"很顺，五个一起跑就可能被预加载拖到超时。
   `项目适配.md` 里的等待写法要注明是在什么条件下试出来的。
   **时红时绿，先怀疑并发**：换回一个浏览器跑，如果稳了，就是被测系统扛不住并发。
   这时候**不要加自动重试来掩盖**，写进 `项目适配.md`，并且作为一条「说不准」报给用户——
   它可能是限流，也可能是真实的性能问题

**跑不稳的脚本不如没有。** 时红时绿几次，就没人再信它了。

## 告诉用户怎么看它跑

用户第一次跑，多半会问"为什么看不到浏览器在动"。提前说：

- 默认不开窗口，快、不打扰人
- 想看全程：用工具的界面模式（Playwright 是 `--ui`），一个窗口，能一步步回放
- 不要推荐"有头模式"看全程：每条测试一个新浏览器，会一直闪。有头模式只适合调单条

## 收尾前：检查要不要写进 `项目适配.md`

逐条过一遍。**有任何一条，就必须写进「踩过的坑」**（做法 / 为什么 / 日期）：

- 换过等待方式（比如这个站不能等网络完全安静）
- 调整过并发（比如只能一个浏览器跑）
- 登录方式跟记录的不一样，或者多用了一个账号
- 为了跑通，改过配置文件
- 撤回过误报，而误报的原因是这个项目特有的
- 某种元素只能用特殊的方式找到

收尾汇报里**必须有一行**：`项目适配.md：补了 N 条（逐条列出）` 或 `项目适配.md：这次没补`。
不能只靠自觉——写没写，要让用户一眼看得到。

## 提到的文件和编号，都写成能点开的链接

谁也记不住 `问题-07`、`已知-05` 底下是什么内容。所以：

- **对话里**：提到文件就写成 `[问题-07](报告/2026-10-10/疑似问题/问题-07.md)`，路径从项目根目录算
- **写进文档里的**（报告、变更单、用例清单、已知 bug、问题单）：每个编号、每个证据文件都写成链接，
  路径从**这份文档所在的目录**算（变更单在 `报告/2026-10-12/` 下，链 10-10 的问题单就写 `../2026-10-10/疑似问题/问题-07.md`）
- 编号链到它的出处：用例 → 那条用例所在的 yaml；问题 → 它的问题单；已知 → `校准/已知bug.md`
- **写完把每个链接对一遍文件在不在**。断掉的链接比没有链接更误导人
- 回放这种点开要下载的，链接旁边照样写上打开它的命令

## 对话长了、被压缩了怎么办

**进度随时落到文件里**：每存好一条，就更新 `用例清单.md` 的「脚本」列。
这样不管是工具自动压缩对话、断网，还是用户中途关掉，都不会白做。

**发现对话被压缩过**（对话开头变成了一段摘要）：**先重读再继续** —— 这个 skill 的说明、
`项目适配.md`、`提示词/02-禁点清单.md`，还有记进度的那个文件。不要凭摘要里的印象往下走，
摘要里不一定还留着禁点清单的每一条。

**这一轮对话已经很长**（走完了一个模块、跑了十几条用例、来回几十轮）：收尾时提醒一句
「下一个命令可以在新对话里打，进度都在文件里」。开新对话比压缩好：压缩留下什么你控制不了，
新对话从文件里读，什么都不会丢。对话不长就不用提。

## 收尾：照这个格式报，一条都不能少

1. **这一步动了哪些文件**：按目录分组，新增还是修改，每个一句话
2. **没动哪些**：列出来
3. **现在去看哪个文件**：指一个具体的
4. **这轮读了几屏、用的哪种读法、大约多少 token**
   token 只能估读页面那一部分，**报的时候说清这不是总数**：每多一轮对话，前面的内容都要重读一遍，
   整个对话的消耗通常是读页面的几十倍，以 AI 工具自己显示的用量为准。有副作用的操作做了几次，也在这一条报
5. `项目适配.md`：补了 N 条（逐条列出）或 这次没补
6. **下一步打哪个命令**

这一步额外要说：存了哪几条（几条正常、几条已知失败）、哪几条没存为什么、
连跑 3 次的结果、以后怎么跑（给出那条命令）。

**收尾时把这几条念给用户听**，让他知道该挑什么毛病（他不会挑，就只能信你说的）：

- 打开 `脚本/` 里刚存的文件：定位用的是看得见的名字，还是 `.css-1x2y`、`//div[3]` 这种
- 有没有 `sleep` 式的死等，等的应该是条件
- **已知失败的那几条，断言写的是正确的样子，还是把 bug 的样子抄成了预期**
- 打开 `用例/用例清单.md`：「脚本」列是不是每条都填了，没存的有没有写原因

然后**停下**。下一轮回归就是 `/qa-4-跑测试`，它会先跑这些脚本。

## 走不通必须上报，不准自己换路

存成脚本时发现原来走通的路现在走不通了：**停下来报告**，不要换一条路让脚本变绿。

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。

目录还是英文名的（`cases/`、`maps/` 这些）：按 `qa-1-建目录` 那个 skill 目录里的 `目录对照.md`
找对应的英文目录，照常做，**不要新建中文目录**。做完提一句：「跑一次 `/qa-1-建目录` 可以改成中文目录」。
