# 写脚本的规矩

**脚本在写用例的同时就写**：扫一个模块、补一条用例，当场写成脚本、当场跑。
没有"先手工跑一遍、以后再存脚本"这一步。回归只在碰到老项目留下的 `草稿`、`未存` 时补写。
之后是不是 bug、预期改没改，**都是改脚本里的一行**，见下面「脚本里的标记」。

用什么工具，看 `项目适配.md` 的「工具」那一段；没写就按 `.qa-ai.json` 的 `端`，
读同目录对应平台文件的「存成脚本用什么」那一节。
定下来的写进 `项目适配.md`，下次不再问。要装工具的（安卓的 maestro 这类），第一次扫之前一次列给用户，他点头才装。

## 从哪写

- **步骤**照 `用例/<流程名>.yaml` 的 `步骤` 一步一步翻，不加步骤、不省步骤
- **点哪里**照 `绑定/` 找；`绑定/` 里没有的，到 `地图/` 里找名字，找到了顺手补进 `绑定/`
- **断言**照 `预期` 写，写的永远是**正确的样子**。页面现在是什么样，跟断言没关系
- **输入**只用 `测试数据/固定数据.json` 里的值

一条用例一个 `test`，放进 `脚本/<流程名>.spec.ts`（别的工具按它的习惯，一个流程一个文件）。

## 定位

只用用户看得见的东西：标题、按钮的名字、角色。不用 CSS class、不用 xpath、不用写死的坐标。
按名字找元素**要精确匹配**：大多数工具默认是"包含"，「登录」会同时匹配到「游客登录」。

## 等待

不要写固定秒数。等一个"确实到了"的标志：

- 页面：等标题出现
- 数据：**等业务接口都返回**，不要等"网络完全安静"。有的前端框架（比如 Nuxt）页面出来后还会预加载别的页面的代码，等"安静"会白等，还会被拖到超时
- 数数：等带关键词的那次请求回来，再数；数字连读两次一样才算数

## 报错要说人话

失败时要说清是哪一步、哪个接口、等了多久。
「有接口没返回」没用，「batch/page 等了 4835ms 没返回」才能查。
每个断言都带一句说明：`expect(行数, '搜完整商品名应该搜到这一条').toBe(1)`。

## 标题以用例编号开头

`test('批次-01 新建批次后是草稿状态', ...)`。
报告、用例、脚本三处能对上，想单跑一条只要按编号筛
（Playwright 是 `npx playwright test -g "批次-01"`，别的工具找等价的筛法，写进 `项目适配.md`）。

## 每条独立

每条从干净的状态开始，不依赖上一条的结果。这样一条挂了不连累下一条。

## 通用巡检放进公共的那个文件

没有崩溃、控制台没有 error、接口没有 5xx、页面上没有 undefined / null / NaN ——
这几条写进 `脚本/工具.ts` 这类公共文件，每条测试结束时自动查一遍。不用每条各写一遍，也不会漏。

## 有副作用的

打开一次扫码量 +1 这种，脚本里也照样会 +1。在那条测试上面写一行注释说明，
`项目适配.md` 的副作用记录里写明「脚本每跑一次 +N」。
同一轮里几条都要打开同一个会计数的页面的，合并成一条测试里打开一次。

## 录回放

失败时自动留回放（Playwright 是 `trace: 'retain-on-failure'`）。通过的不留。

## 脚本里的标记：bug 和脚本一起改

断言永远写**正确的样子**（有原文的照原文，基线照扫的时候的样子）。现在不成立的，加一个已知失败标记，
标记里写清它在等什么。**一条测试只有这几种状态**，每种对应 `用例清单.md` 「脚本」列的一种写法：

| 标记 | 什么时候加 | 什么时候改 |
| --- | --- | --- |
| 没有标记 | 通过，或者没变 | — |
| `test.fail(true, '问题-07 待确认：保存成功列表里没有')` | 断言挂了，过了缺陷门槛，刚写问题单 | 用户说是 bug → 改成 `已知-05`；说不是 → 按他说的改断言，删掉标记 |
| `test.fail(true, '已知-05：草稿标签公开可见，等修')` | 用户确认是 bug | 修好了（本该失败却通过了，核实过）→ 删掉标记 |
| `test.fail(true, '变了：批次-01 以前显示草稿，现在待提交')` | 基线挂了 | 用户说变得对 → 改断言、删标记；说变错了 → 改成 `已知-xx` |

改法就是 `qa-3-审完了/审核表.md` 「他说「审完了」：一次改齐」那张表。**标记和问题单、用例清单永远一起改**，不留"问题单说已修、脚本还标着等修"这种对不上的。

这种写法有个漏洞：标了已知失败，**因为任何原因失败都算意料之中**，页面改版点不到按钮也会被吞掉。所以：

- 断言 bug 的那一句前面，**先把前提断言一遍**（页面打开了、看到了一级标题），让别的失败尽早暴露
- 跑的时候核对它**失败在哪一行**（`回归.md` 的「已知失败的那几条要多看一眼」）

用的工具没有「已知失败」这种标记的：这条先跳过（`skip`），跳过的原因写同样的话，`用例清单.md` 照写。

## 写完当场跑，跑稳才算存好

1. 一个模块的脚本写完，**先单线程跑一次**：挂了先分清是脚本没写对还是系统的问题（见 `回归.md` 「脚本第一次跑就挂了」）
2. 脚本对了之后**再连跑两次**，三次结果一样才算存好，「脚本」列写 `已存`
3. 时红时绿的：先改等待；改两次还不稳，从脚本里拿掉，写 `未存：时红时绿 · <卡在哪>`。
   **不要加自动重试来掩盖**。换回单个环境跑稳了的，是被测系统扛不住并发，写进 `项目适配.md`
4. 想并行再试并行。单个环境下试出来的等待写法，并行时不一定成立，`项目适配.md` 里注明是什么条件下试的

**跑不稳的脚本不如没有。** 时红时绿几次，就没人再信它了。

## 告诉用户怎么看它跑

- 默认不开窗口，快、不打扰人
- 想看全程：用工具的界面模式（Playwright 是 `--ui`），能一步步回放
- 不要推荐"有头模式"看全程：每条测试一个新浏览器，会一直闪。有头模式只适合调单条
