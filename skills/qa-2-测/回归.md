# 回归：跑存好的脚本，出报告

`/qa-2-测` 定了这次要回归时读这份。

## 这轮跑什么

用户说的话对应跑什么：

| 他说 | 跑什么 |
| --- | --- |
| 「跑批次发布」「回归一下批次那块」 | `用例/` 里 `流程: 批次发布` 的全部 |
| 「跑批次-02 到批次-04」 | 这几条 |
| 「全部跑一遍」 | `用例/` 里所有的 |
| 「跑冒烟」 | `用例/` 里 `范围: 冒烟` 的那批 + `脚本/` 里存好的。**这批不能有累积、不可逆、对外可见的副作用**；计数类（扫码量 +1）可以，记进副作用记录 |
| 「跑全量」 | 全部，包括会留痕迹的 |
| 没说（只打了 `/qa-2-测`） | 存好的全部，`范围: 全量`（会留痕迹）的除外；有全量的，放进计划表「这次不做」，他点名了才跑 |

跑几条、哪几个流程、大概多久、会不会动数据，都写进 `SKILL.md` 第 4 节那张计划表，他说「开始」再跑。

**这几种不跑**，跳过几条要报出来，别判成失败：

- `状态: 待实现`：功能还没做出来（开发阶段照 PRD 先写的）
- `状态: 待数据`：缺前置数据
- `范围: 要用户准备`：**用户没明说"可以跑"就不跑**，更不要自己删数据去腾位置

把这些判成失败，等于天天红，没人再看报告。

## 跑之前先做环境体检

下面任何一项不对，**全部用例都会红，而且红得跟被测系统毫无关系**。先查，不对就停下来报告：

| 查什么 | 怎么查 |
| --- | --- |
| 登录态还有效 | 拿它打开一次首页看显示的是谁。账号密码登录的，过期了登录脚本会自己重登（见平台文件「登录态」）；重登也失败才算问题 |
| 要用到的每个域名的证书没过期 | 读证书的有效期，不要靠"打开页面没报错"判断 |
| 网络能直连 | 本机开了代理的，代理可能掐断某些域名的连接。**命令行工具和浏览器走不走代理不一样**，一个通一个不通时，先怀疑代理 |

体检发现的问题分两种：

- **环境的问题**（重登失败、要验证码、本机代理）：不是 bug，请用户处理，处理完再跑
- **被测系统的问题**（证书过期、域名打不开）：**这是线上事故，直接报，标紧急**。
  不要忽略证书错误硬打开，也不要换个域名绕过去 —— 绕过去了，报告里是"通过"，用户那边是打不开

## 开始前

1. 看 `用例清单.md` 的「脚本」列：`已存` 的直接跑；`草稿`、`未存` 的（老项目留下的），**先补成脚本再跑**，见下一节
2. 读 `缺陷门槛.md`、`校准/已知bug.md`、`校准/不算bug.md`（有就读），挂了的照它们判
3. 告诉用户：这轮跑哪些、大概多久、**能不能看、怎么看**。

跑的过程中，每跑完一条用例报一句结果。不要闷头跑完才开口。

## 怎么跑：跑脚本，只看挂了的

脚本在扫页面、补用例时就存好了。**回归不探索、不一页一页去点**：

1. **跑**：用测试工具跑这一轮要跑的，结果写成文件（Playwright 用 json 报告）
2. **读**：读结果文件，通过的直接记通过（基线的记「没变」），依据就是那条断言。**不用为通过的再去打开页面看**
3. **看挂了的**：只有挂了的那几条，AI 打开回放或者亲自走一遍，分清是哪种（见下一节），再照 `缺陷门槛.md` 判

**老项目留下的**：「脚本」列是 `未存` 的，照 `写脚本.md` 现写；是 `草稿` 的（1.6.0 写的），对一遍 `写脚本.md` 的规矩，
不合的改掉（比如为了跑通写的固定等几秒），已知 bug 的补上标记，再连跑三次，稳了改成 `已存`。
预期来源是 `AI推测` 的，照基线对待：挂了只报变了。

写不成脚本的，AI 照用例手工走：要看排版、看图、读文案通不通顺这类非看不可的。
「脚本」列写 `不适合存：<原因>`。

`用例/` 里的步骤是业务语言，`绑定/` 里是页面上的位置。**界面改了只改 `绑定/`，`用例/` 一个字都不动。**

## 脚本第一次跑就挂了：先分清是谁的错

第一次写的脚本，挂了不一定是被测系统的问题，也可能是脚本自己没写对。**先分清，再判**：

| 挂在哪 | 多半是 | 怎么办 |
| --- | --- | --- |
| 找不到元素，但 `地图/` 里记着它、页面上现在**也有** | 脚本写错了（名字不精确、等早了） | 改脚本再跑。**不算判定**，不进报告 |
| 找不到元素，页面上现在**真的没有了** | 页面改了 | **走不通，判「说不准」**，见「走不通必须上报」。不准换条路让它过 |
| 断言没过 | 可能是 bug，也可能只是变了 | 按「下结论之前，先核实一次」核实，再照 `缺陷门槛.md` 判：缺陷、变了、还是说不准 |
| 时红时绿 | 等待或并发 | 先改等待；还不稳就判「说不准」，写明 |

一条脚本改了两次还跑不通，就停下，判「说不准 · 脚本没写通」，写明卡在哪。不要一直改下去。

**同一条用例上一轮已经报过问题、还在 `待确认` 的**，这轮又挂在同一个地方：在原来那份问题单里补一句「<日期> 又出现」，
不另起新编号，审核表里也不重复列。

## 已知失败的那几条要多看一眼

脚本里标了已知失败的（`test.fail`，标记写着 `已知-xx`、`问题-xx 待确认` 或 `变了`，见 `写脚本.md` 「脚本里的标记」），结果有三种：

| 结果 | 说明什么 | 怎么报 |
| --- | --- | --- |
| 失败，**失败在标记说的那一句断言上** | 还是老样子 | 报告里一行「已知-05 还没修」「问题-07 还在等你定」，不算新问题 |
| 失败，**失败在别处**（比如前提断言、点不到按钮） | 出了新情况，被标记吞掉了 | **当新情况判**：照缺陷门槛，写明失败在哪一行 |
| **本该失败却通过了** | 可能修好了（或者变回去了） | AI 照用例再走一遍核实；核实了，进审核表「已知 bug 可能修好了」，**标记先不去**，他审完再去 |

失败在哪一行，读工具的结果文件就知道（Playwright 的 json 结果里有 `errorLocation`），不用截图。

## 跑完回写用例清单

每跑完一条，改 `用例/用例清单.md` 的「最近判定」列：`通过 · 10-12`、`没变 · 10-12`、`失败 · 已知-05`、`失败 · 问题-07`、`变了 · 10-12`、`说不准 · 接口层没验`。
**这一列和「脚本」列是下一个对话的记忆**：新开的对话只读这张表，就知道哪些在等什么。

## 判定三档，不是两档

| 判定 | 什么时候用 |
| --- | --- |
| `通过` | 符合预期，**且你能指出依据**。预期来源是 `基线`、`AI推测` 的，通过了只能叫 `没变` |
| `失败` | 违反了某条明确写下来的规则，**而且过了 `缺陷门槛.md`** |
| **`说不准`** | 规则没覆盖到 / 依据模糊 / 你也不确定 / 走不通 |

基线挂了，判定写 `变了`。它算在「说不准」这一档里（对不对没人知道），但报告里单独数，不混进别的说不准。

> **「说不准」不是失职，是最有价值的输出。硬着头皮下结论才是。**

一轮里 `说不准` 占 10~20% 是健康的。
接近 0 说明在硬判，超过 40% 说明 `用例/` 写得太含糊 —— 两种都要说出来。

**没有「部分通过」这一档。** 一条用例只验了一半（比如「看不到、改不了」只验了「看不到」）：
验了的那半是通过，没验的那半就是 `说不准`，整条判 `说不准`，写明哪一半没验、为什么。
合计里不准把它算进通过。这种用例下次补用例时拆成两条，各判各的。

## `预期来源` 决定这条最高能判到什么

| `预期来源` | 最高能判 |
| --- | --- |
| `PRD` / `产品说明` / `通用规律` / `用户确认` | 通过；挂了照缺陷门槛判失败 |
| **`基线`**、**`AI推测`**（老的） | 过了只叫 `没变`，**不算进通过**；挂了只叫 `变了`，**不报 bug** |
| **`冲突待裁决`**（PRD 跟成品对不上） | **只能判「说不准」**，把两边差异列出来，人来裁决 |

照现状写的预期，跟系统现在的行为一对，当然是"符合"——这不能叫通过，
**不然就是拿系统证明系统，bug 会被原样判成通过。** 所以报告里「通过」和「没变」分开数。

## 判定必须带依据

不要只给结论。**人 review 的是依据，不是结论** —— 依据对不对一眼看得出来，结论对不对看不出来。

**只有过了 `缺陷门槛.md` 的失败才写问题单** `疑似问题/问题-xx.md`，脚本那条标上 `问题-xx 待确认`，审核表「是不是 bug」加一行。
变了的、说不准的**不写问题单**：变了的进审核表「变了，变得对不对」；说不准的报告里一句话写清卡在哪。
**编号接着整个项目往下排**：
先看所有 `报告/*/疑似问题/` 里最大的号，从下一个开始，换一天不从 01 重来。

问题单**用 Markdown，不用 JSON** ——
人要点开来读，JSON 满屏引号和括号没人看得下去：

```markdown
# 问题-01 · 满100减20券在99元订单上可选中，点击后报系统错误

| 项 | 内容 |
| --- | --- |
| 用例 | [优惠券-07](../../../用例/优惠券.yaml) |
| 规则 | PRD 3.2 · 订单满 100 元才能用满减券 |
| 判定 | 失败 |
| 平台 | 状态：待确认 · 单号：无 |

## 步骤
1. 进入购物车（99 元）
2. 点去结算
3. 选「满100减20」

## 预期
券置灰，提示还差 1 元

## 实际
券可选中，点击后弹「系统错误」

## 依据
PRD 3.2 写了门槛校验应在选择时拦截，这里没拦截且报了未定义错误

## 证据
- 回放：[优惠券-07-回放.zip](../证据/优惠券-07-回放.zip)（`npx playwright show-trace 报告/2026-09-20/证据/优惠券-07-回放.zip`）
- 页面结构：[优惠券-07-页面结构.yaml](../证据/优惠券-07-页面结构.yaml)

**换个端，证据换成等价的那样**（具体命令见平台文件）：安卓是截图或录屏加界面树加 `logcat`
（崩溃必须带 `-b crash` 那一段，还要写清机型和系统版本）；小程序是截图加页面数据加控制台和网络面板。
**哪个端都一样：失败和说不准的那条，证据必须能让开发自己复现。**
- 控制台：`TypeError: Cannot read properties of undefined (reading 'threshold')`
- 网络：`POST /api/coupon/apply → 500`
```

下面「走不通」「断点」那几段，也是写进问题单里的小节。

## 下结论之前，先核实一次

AI 最容易犯的不是漏报，是**误报**。判「失败」之前，换一种方式再确认一次（这是缺陷门槛第二关的第 2 条）：

| 看到的 | 先查什么 |
| --- | --- |
| 两个数字对不上 | 标签是不是同一个口径（累计 vs 本月、全部 vs 已发布） |
| 界面上一列是空的 | **看接口有没有返回这个数据**：有 → 前端没显示；没有 → 后端没给。这决定了该找谁修 |
| 读取工具说某个元素没名字、不存在 | 直接看元素里的文字，读取工具的显示模式可能不全 |
| 时红时绿 | 先怀疑并发和等待，不要先怀疑被测系统 |

核实后发现是误报的，**不删，写进报告的「核对后撤回的」**。
用户看到你撤回过什么，才敢信你留下的。

**不汇总别人的个人信息**：页面上看到别人的 IP、手机号、邮箱，记下"显示了"就行，
不要去收集、统计这些值来证明是 bug。证据里也不要写这些值。

## 通用巡检（不需要 PRD，每轮都跑）

在走过的每个页面上验：

```
- 没有崩溃、白屏、错误页
- 控制台没有 error，网络没有 5xx
- 界面上不出现 undefined / null / NaN / [object Object]
- 返回键能回上一页，不卡死
- 关键数字自洽：总额 = 各分项之和
- 任意输入框塞 500 字符不崩
```

这层最划算：**答案不依赖需求，你自己就能判**，而且人最不爱干。
巡检已经写在脚本的公共文件里，跑脚本就带上了。命中的都是 `缺陷门槛.md` 里的硬规律，照常写问题单；
**控制台有 error 但功能是好的，不报**。

## 走不通必须上报，不准自己换路

用例第 3 步的按钮点不到时：

```json
{
  "判定": "说不准",
  "走不通": {
    "计划": "点商品详情页的「加入购物车」",
    "实际": "该按钮不存在",
    "看到的": ["立即购买", "收藏", "分享"],
    "我没做的事": "没有改用列表页的快捷加购"
  }
}
```

**你绕过去了，bug 就被埋了。** 这是整套流程里最容易犯、代价最大的错。

## 跨系统用例（`用例/` 里有 `谁:` 或 `对账:` 时）

**多个账号**：一个环境同时只能登一个账号。Web 是每个角色开一个互相隔离的浏览器环境，
各带各的登录状态；安卓和小程序没有"一份文件换一份"这回事，要么退出重登、要么多准备一台设备
或一个微信号，怎么安排写进 `项目适配.md`。不管哪个端，**不要在同一个环境里反复退出再登**。

**等待**：轮询到条件成立，不准固定 sleep。超过用例里写的时限就判失败 ——
时限到不了本身就是 bug，不是"环境慢"。

**上下游：流程走完不算通过，字段对账全部相等才算。**
按 `绑定/` 的「ID对照」串起链路，按「数据位置」逐字段取值比对。

**挂了必须报出断在哪一跳**，不能笼统说失败：

```json
{
  "判定": "失败",
  "断点": "第 2 跳：订单系统 → 财务系统",
  "已确认": "订单系统下单成功，orderNo 20260921-0043，接口 200",
  "未发生": "财务系统 60 秒内查不到 outNo=20260921-0043",
  "还没查的": "消息有没有投递 / 是不是被过滤条件挡了"
}
```

跨系统的 `说不准` 比例会明显偏高 —— 边界上谁的锅本来就不清楚。
这是正常形态，在报告里说明，不要为了压比例硬判。

## 每条都要能回放，但只留该留的

跑的时候**每条都录**：Web 是 Playwright 的 trace，安卓是录屏（模拟器上经常录不了，就退回连续截图），
小程序是开发者工具的截图加网络记录。用户不信哪一条，点开就能一步步看你做了什么。

录了不等于都要留下来。一条回放几百 KB 到一两 MB，一轮十几条就是十几 MB，一个月下来项目里全是 zip：

| 这条 | 回放放哪 |
| --- | --- |
| 写了问题单的失败、变了的 | **放进 `报告/<日期>/证据/`，长期留**。要进问题单、要给用户看变成了什么样 |
| 已知 bug 这轮没复现（可能修好了） | 同上，要拿去关单 |
| 说不准（没写问题单） | 留在工具的输出目录，跟通过的一样，报告里那句话写清卡在哪就够 |
| 通过 | **不放进 `证据/`**。留在工具自己的输出目录里（见 `项目适配.md`，一般是 `.playwright/`），下一轮会被覆盖。报告里不给链接，结尾写一句「通过的回放在 XX，下一轮会被覆盖，要长期留就说一声」 |

**解压回放来看的，解到临时目录，看完删掉**，不要解在 `证据/` 里 —— 解开就是几十个零碎文件。

一轮没有要他定的，就**不写审核表**，也不写 `疑似问题/`。

## 报告：先结论，正常的一行带过

报告是给人看的，**打开第一屏就要知道三件事：能不能发版、有几个新问题、要他做什么**。
细节不是不要，是放对地方：每条失败的步骤、接口、元素原文写在问题单里，报告里一句话加链接。

**整份报告控制在 40 行左右。** 写长了，要紧的那两行会被埋掉。照这个样子：

```markdown
# 冒烟测试报告 · 2026-10-15

生成：QA 流水线 v<版本号> · qa-2-测 · <日期>

**17 条：通过 9、没变 4、失败 4、变了 0、说不准 0。新问题 2 条等你定，已知 bug 2 条还没修。不能发版。**

**没验什么**：新建、发布这些写操作一条没跑；表单校验、筛选、翻页、导出没有用例。
全项目 12 个模块，有用例的 4 个，见 [覆盖表](../../地图/覆盖表.md)。

## 要你定的
```

几条规矩：

- **第一行就是结论**，不要先铺垫环境、范围。「没验什么」紧跟在结论后面，不准挪到结尾：用户看到「通过」两个字，默认会以为功能测过了。
  只跑了冒烟的，说得更直白：**「这轮只验证了页面能打开，功能一个都没测」**
- **依据一句话**，写看到了什么（「只剩这一条」「6 → 7」），不写接口路径、等待写法、元素属性。那些要么进问题单，要么不写
- **正常的一行带过**：环境体检、已知 bug、巡检、副作用，没事就各一行；有事才展开成表
- **不重复**：结论那一行已经有合计了，不要再出一张合计表；回放怎么打开写在问题单里，报告里不再教一遍
- 「说不准」接近 0 或超过四成的，在结论下面加**一句**为什么，不要写成一段
- **「通过」和「没变」分开数**。没变的多，结论下面加一句：「没变的 N 条只说明跟上次一样，没验对不对」
- 「要你定的」只是一句话加审核表的链接，**不把审核表的内容抄进报告**
- 「核对后撤回的」一定要有（有撤回才写），一条一句。用户看到你撤回过什么，才敢信你留下的

## 副作用算没算，量出来，别猜

做了一个可能会计数的操作（打开扫码地址、看一篇文章），**不知道算不算一次的，跑前跑后各读一次那个数**，
报告里写实数：「扫码量 12 → 13」或「没变，草稿不计数」。
不准写「如果草稿也计数的话」这种话 —— 你能量，就不该让用户去猜。
量的时候要多开一个页面、多登一个账号的，照常做，但这次读法和多花的 token 一并写进收尾。
量出来的结论（什么计数、什么不计）写进 `项目适配.md`，下次不用再量。

## 收尾前自己查

- `报告/<日期>/报告.md`：第一行是不是结论，紧跟着是不是「没验什么」；整份是不是 40 行左右，正常的是不是一行带过
- 每条判定后面有没有一句依据；失败的有没有写**该找谁修**
- `证据/` 里：有问题单的、变了的每条都有回放；**通过的没有放进来**；没有解压出来的零碎文件
- 这轮跑的每条，「脚本」列都有值；老项目的 `草稿` 都定稿了；**没有用完就扔的临时脚本**
- **每张新问题单都过了缺陷门槛**：能指出原文或硬规律；没有一张是基线挂了、叫法不一致、样式这类
- 问题单、脚本标记、用例清单三处对得上：有 `问题-xx` 的，脚本标的就是 `问题-xx 待确认`
- `说不准` 接近 0 或者超过 40%，有没有解释
- **对照 `校准/已知bug.md`：已知的 bug 这轮抓到了没有**。
  抓不到就说明这套东西在装瞎，其他结论一概不能信
