# 第 5 步 · 提 bug

## 只在用户确认之后执行

`报告/*/疑似问题/` 里的是**疑似**，不是 bug。

**动 bug 平台是外发动作。** 提错单、关错单，要在群里道歉的是人，不是你。
不要接到流水线里自动跑。

## 价值不在省填表的 5 分钟，在证据完整

人手工提 bug 会偷懒：不附日志、复现步骤写两行、不贴网络请求。
你整理的单天生带全套，**开发那句"我这儿复现不了"直接消失大半**。

## 开始前

1. 读 `项目适配.md` 的「bug 平台」那一段：用的什么平台、**关联方式是哪种**。
   没写 → 按「不关联」做，收尾时问一句要不要接平台
2. 读所有 `疑似问题/问题-xx.md` 和 `校准/已知bug.md`，看每条现在是什么状态。
   **这一步不靠聊天记录**：上次谈到哪、哪张单已经提了，全在这些文件里
3. 用户这次要确认的问题，**逐条列给他：是 bug / 不是 bug / 先放着**

## 三种关联方式，用户选

| 方式 | 你能做什么 | 适合 |
| --- | --- | --- |
| **不关联**（默认） | 不碰平台。每次出一张变更单，**人照着改**，改完把单号告诉你 | 不放心 AI 动平台、平台没有接口、刚开始用 |
| **只读** | 能查：查重、看单子现在什么状态。**不能改**，变更单照样人改 | 想要查重和状态同步，但不想让 AI 写 |
| **可写** | 按变更单逐条改。**每一条改之前都给用户看、等他点头** | 用顺了、信得过了 |

**不关联不是降级。** 整理单子、找证据、查哪些该关，这些最费时间的活你照样全做；
人只做最后"粘贴、点保存"那一下。

哪种方式下都**不准做**：删单；改不是这套流程提的单；一次改一批而不逐条列出。

## 变更单：每次都出，不管哪种方式

一轮测完，平台上要动的远不止"新建"。按这几类整理，写进 `报告/<日期>/bug平台变更单.md`：

| 类别 | 从哪来 | 要做什么 |
| --- | --- | --- |
| **新建** | 用户刚确认是 bug、还没有单号的 | 完整的单子内容（见下面「单子写什么」） |
| **补充** | 已有单号，这轮又复现了、或者有了新证据 | 在原单下补一条：哪天、哪个版本、复现率、新证据 |
| **可以关闭** | 已知失败的脚本「本该失败却通过了」，并且核实过 | 核实的方法和证据，建议关闭 |
| **重新打开** | 平台上已关闭的，这轮又出现了 | 原单号 + 这次复现的证据 |
| **疑似重复** | 跟平台上已有的单很像 | 列出两边，**请用户判断**，不要自己决定跳过 |
| **撤回** | 之前报过、这轮核实发现是误报 | 原单号 + 为什么是误报 |

每一条都写成**能直接复制粘贴**的样子：平台上哪个字段填什么，按 `项目适配.md` 里的字段对照来。
没有字段对照，就按下面那份通用格式写。

```markdown
## 新建 · 问题-07 → 已知-05
标题：[追溯页] 别家没发布的草稿标签，消费者不登录也能看到全部内容
严重程度：高
……（完整内容）

## 可以关闭 · 平台单号 TJT-118（已知-02）
核实：10-12 脚本「审批-01」本该失败却通过了；AI 照用例重走一遍，6 处审批入口都已经没有了
证据：报告/2026-10-12/证据/审批-01-回放.zip
```

变更单最后附一句：**改完了，把新单号告诉我，我写回去。**

**不要给单子另起一套编号。** 变更单里每条就用它本来的 `问题-xx`（确认后还有 `已知-xx`），
提到平台之后用平台给的单号。同一个 bug 已经有两个号了，再起一个 `B-01`，人就得记三个号对一张单。

## 每条问题的平台状态，记在问题单里

问题单表格里的「平台」那一行：

```markdown
| 平台 | 状态：已新建 · 单号：TJT-123 · 同步于 2026-10-12 |
```

状态只有这几个：`待确认`（`/qa-4-跑测试` 刚写的，用户还没说是不是 bug）/ `待新建` / `已新建` / `待补充` / `待关闭` / `已关闭` / `待重开` / `不提`。

**变更单就是从这些状态生成的**，所以换一个对话、隔一个星期，照样能接着出。
用户说「TJT-123 建好了」，你把单号和状态写回去，`校准/已知bug.md` 里那条也写上单号。

## 单子写什么

```markdown
### [购物车] 满100减20券在99元订单上可选中，点击后报系统错误

- 严重程度：中
- 模块：优惠券
- 发现方式：用例 [优惠券-07](../../用例/优惠券.yaml)，问题单 [问题-01](疑似问题/问题-01.md)
- 环境：地址 ……，版本 v2.4.1-rc3，浏览器 Chromium 131
- 前置条件：账号 qa01（[固定数据](../../测试数据/固定数据.json)），持「满100减20」券，购物车小计 99 元
- 复现步骤：
  1. 打开 /cart
  2. 确认小计显示 ¥99.00
  3. 点「去结算」
  4. 在优惠券行点「满100减20」
- 预期：券置灰不可选，提示「还差 1 元」（PRD 3.2）
- 实际：券可选中，点击后弹「系统错误」，订单页卡住
- 复现率：3/3
- 证据：回放、页面结构、控制台、网络，每个都是链接
- 疑似重复：无
```

**复现步骤要精确到每一次点击**，让开发照着点就能复现。这是整张单最值钱的部分。

**提之前，没有副作用的再复现一次。** 问题是几天前发现的，系统可能已经改了：
只读的页面（企业端列表、首页文案）重走一遍，复现率写成 `2/2 · 10-09、10-12`；
**有副作用的**（打开一次扫码量 +1）不用为了凑次数再开，但要在复现率后面写明「只验过 1 次，因为每开一次扫码量 +1」。
复现不出来了：不进「新建」，单独列给用户，可能已经修了，也可能是偶发。

**证据里不写别人的个人信息**（IP、手机号、邮箱），写"页面显示了"就行。

## 跨系统的单：不要猜是谁的锅

模块填链路（`订单系统 → 财务系统`），标题里带断点，**两边的证据都附上**。
不要自己判断该指派给哪个团队 —— 猜错了，这张单会在两个团队之间踢三天。

## 查重

> 自动提单最容易产生的不是错单，是重复单。

- **只读 / 可写**：用标题关键词搜平台上还没关的单，命中的放进变更单的「疑似重复」
- **不关联**：你搜不了，就在变更单里给出**建议的搜索关键词**，请用户提之前搜一下

## 要接平台的时候

用户说「接一下我们的 bug 平台」，或者从「不关联」改成「只读」「可写」：
**读同目录的 `接平台.md`，照着一步步带他接。** 任何平台都行，不限于哪几家。

## 用户确认之后，落到文件里

用户确认是 bug 的，**不管提没提到平台**，都要落到文件里，下一个对话才接得上：

- 进 `校准/已知bug.md`，给一个 `已知-xx` 编号，写明从哪个 `问题-xx` 来、哪条用例抓到的
- `用例/用例清单.md` 那条用例的「最近判定」改成 `失败 · 已知-xx`
- 问题单的「平台」那一行改成 `待新建`（不提平台的写 `不提`）
- 用户说不是 bug 的：问题单里写上「用户确认不是 bug · 日期 · 原因」。
  **是用例的预期错了，就去改用例**，不然下次还会报同一条

## 提到的文件和编号，都写成能点开的链接

谁也记不住 `问题-07`、`已知-05` 底下是什么内容。所以：

- **对话里**：提到文件就写成 `[问题-07](报告/2026-10-10/疑似问题/问题-07.md)`，路径从项目根目录算
- **写进文档里的**（报告、变更单、用例清单、已知 bug、问题单）：每个编号、每个证据文件都写成链接，
  路径从**这份文档所在的目录**算（变更单在 `报告/2026-10-12/` 下，链 10-10 的问题单就写 `../2026-10-10/疑似问题/问题-07.md`）
- 编号链到它的出处：用例 → 那条用例所在的 yaml；问题 → 它的问题单；已知 → `校准/已知bug.md`
- **写完把每个链接对一遍文件在不在**。断掉的链接比没有链接更误导人
- 回放这种点开要下载的，链接旁边照样写上打开它的命令

## 收尾：照这个格式报，一条都不能少

1. **这一步动了哪些文件**：按目录分组，新增还是修改，每个一句话
2. **没动哪些**：列出来
3. **现在去看哪个文件**：一般是 `报告/<日期>/bug平台变更单.md`
4. **这轮读了几屏、用的哪种读法、大约多少 token**；有副作用的操作做了几次
5. `项目适配.md`：补了 N 条（逐条列出）或 这次没补
6. **下一步打哪个命令**

这一步额外要说：变更单里每一类各几条；可写方式下实际改了几条、单号是多少；
还有几条在等用户改完告诉你单号。

**收尾时把这几条念给用户听**，让他知道该挑什么毛病（他不会挑，就只能信你说的）：

- 打开变更单：复现步骤是不是精确到每一次点击，开发照着点就能复现
- 有没有带环境、账号、时间、证据路径
- 「可以关闭」的每一条，有没有写怎么核实的；只凭脚本变绿就建议关单是不够的
- 疑似重复的，是不是留给他判断，而不是自己跳过了

然后**停下**。下一步：

- 用户还要去平台上改的 → 改完回来说一声单号，再打 `/qa-5-提bug` 写回去
- `用例清单.md` 里有通过了、「脚本」还是未存的，或者刚确认了已知 bug 的 → `/qa-6-存成脚本`。
  现在做或过几天做都行，状态在文件里
- 都没有 → 下次提测再 `/qa-4-跑测试`

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。

目录还是英文名的（`cases/`、`maps/` 这些）：按 `qa-1-建目录` 那个 skill 目录里的 `目录对照.md`
找对应的英文目录，照常做，**不要新建中文目录**。做完提一句：「跑一次 `/qa-1-建目录` 可以改成中文目录」。
