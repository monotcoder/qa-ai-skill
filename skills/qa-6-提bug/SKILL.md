# 第 6 步 · 提单

## 只在用户确认之后执行

`报告/*/疑似问题/` 里的是**疑似**，不是 bug。

**提单是外发动作，每次都要用户点头。** 不要接到流水线里自动跑 ——
提错单要在群里道歉的是人，不是你。

## 价值不在省填表的 5 分钟，在证据完整

人手工提 bug 会偷懒：不附日志、复现步骤写两行、不贴网络请求。
你提的单天生带全套，**开发那句"我这儿复现不了"直接消失大半**。

## 字段

```json
{
  "标题": "[购物车] 满100减20券在99元订单上可选中，点击后报系统错误",
  "严重程度": "中",
  "模块": "优惠券",
  "发现方式": "用例 C-07",
  "环境": { "地址": "...", "版本": "v2.4.1-rc3", "浏览器": "Chromium 131" },
  "前置条件": "账号 qa01（测试数据/固定数据.json），持「满100减20」券，购物车小计 99 元",
  "复现步骤": [
    "1. 打开 /cart",
    "2. 确认小计显示 ¥99.00",
    "3. 点「去结算」",
    "4. 在优惠券行点「满100减20」"
  ],
  "预期": "券置灰不可选，提示「还差 1 元」（PRD 3.2）",
  "实际": "券可选中，点击后弹「系统错误」，订单页卡住",
  "复现率": "3/3",
  "证据": { "aria快照": "...", "控制台": "...", "网络": "...", "trace": "..." },
  "疑似重复": []
}
```

**复现步骤要精确到每一次点击**，让开发照着点就能复现。这是整张单最值钱的部分。

## 跨系统的单：不要猜是谁的锅

模块填链路（`订单系统 → 财务系统`），标题里带断点，**两边的证据都附上**。
不要自己判断该指派给哪个团队 —— 猜错了，这张单会在两个团队之间踢三天。

## 提交前查重

用标题关键词搜平台上还 open 的单，命中就填进 `疑似重复`，**提示用户，不要自己决定跳过**。

> 自动提单最容易产生的不是错单，是重复单。

## 三档实现

| 档 | 做法 | 成本 | 收益 |
| --- | --- | --- | --- |
| **1** | 输出上面这个 JSON / Markdown，**用户复制粘贴** | **0** | **80%** |
| 2 | 跑 `工具/提bug.ts` 调平台 API | 半天 | +15% |
| 3 | 平台 MCP，直接提 | 1 天 | +5%，主要是爽 |

**没配平台就走第 1 档，直接把整理好的内容打出来。**
不要因为没有 API 就说做不了 —— 第 1 档已经拿到 80% 的价值。

## 提完

把平台返回的单号回写进那个 `疑似问题/F-xx.json`，闭环。

## 收尾：照这个格式报，一条都不能少

1. **这一步动了哪些文件**：按目录分组，新增还是修改，每个一句话
2. **没动哪些**：列出来
3. **现在去看哪个文件**：指一个具体的
4. **这轮读了几屏、用的哪种读法、大约多少 token**；有副作用的操作做了几次
5. `项目适配.md`：补了 N 条（逐条列出）或 这次没补
6. **下一步打哪个命令**

这一步额外要说：提了几张、单号是多少、哪些因为疑似重复没提。

**收尾时把这几条念给用户听**，让他知道该挑什么毛病（他不会挑，就只能信你说的）：

- 复现步骤是不是精确到每一次点击，开发照着点就能复现
- 有没有带环境、账号、时间、证据路径
- 提之前查没查重

然后**停下**。这是流水线的最后一步，回到 `/qa-4-跑测试` 开始下一轮。

## 老项目缺文件时

项目是旧版建的、缺了这一步要读的某个文件：**按没有它的方式照常做，不要报错停下**。
做完最后提一句：「新版多了 XX，可以跑一次 `/qa-1-建目录` 补上」。

目录还是英文名的（`cases/`、`maps/` 这些）：按 `qa-1-建目录` 那个 skill 目录里的 `目录对照.md`
找对应的英文目录，照常做，**不要新建中文目录**。做完提一句：「跑一次 `/qa-1-建目录` 可以改成中文目录」。
